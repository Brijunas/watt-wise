# Accounts

The account is the user: its id, preferred language and creation time, and everything the user owns hangs off it. This doc is how the feature is built: the model, ASP.NET Core Identity, the emails it sends and the account flows: registration and confirmation (S4.3), then sign-in and the rest. Each E4 story adds its section here. What the feature enforces (passwords, lockout, tokens, sessions, permissions) is decided in the root [security.md](../../../docs/security.md); the token flow seen by clients is in the root [technical.md](../../../docs/technical.md#backend).

## Emails

The account flows send three messages, each in the account's preferred language (LT or EN). They are records in Application's `Accounts/`; S4.2 built the sending, the stories below build and send them ([email.md](../email.md)).

| Message                     | What it says                                                                         | Requested by                             |
| --------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------- |
| `EmailConfirmationEmail`    | Confirm your email with this link, valid 24 hours; ignore this if you didn't sign up | S4.3, on registration and on resend      |
| `AccountAlreadyExistsEmail` | Someone tried to sign up with your email, which already has an account; no link      | S4.3, on registration with a taken email |
| `PasswordResetEmail`        | Set a new password with this link, valid 1 hour; ignore this if you didn't ask       | S4.5, on forgot password                 |

A use case only records the request; the Jobs host sends it ([email-outbox.md](../email-outbox.md)). Link lifetimes and the no-account-discovery rule are in [security.md](../../../docs/security.md#accounts).

## Model

ASP.NET Core Identity in Infrastructure, on `AppDbContext`, handles the account's `AccountIdentity`: password hashing, lockout, email tokens and (later) external OAuth logins.

- **Five groups of tables** in the `app` schema:
  - **Account:** `accounts` (Domain `Accounts/Account`).
  - **Authentication:** `identity_users` (one per account, `account_id` unique), `identity_user_logins` and `identity_user_tokens` (kept for OAuth, unused), `email_link_tokens` (one per `AccountIdentity` and purpose).
  - **Authorization:** `roles`, `account_roles`, `permissions`, `role_permissions` (Domain `Accounts/Role`, `Permission`, and the link entities `AccountRole`, `RolePermission`).
  - **Sessions:** `sessions` (Domain `Accounts/Session`: device label, sign-in time, last use) and `refresh_tokens` (its `RefreshToken`s: SHA-256 `token_hash`, unique, issue and expiry times, `used_at`). Both cascade from `accounts`, and the tokens from their session. `refresh_tokens` has a concurrency guard on PostgreSQL's `xmin`, so two refreshes with one token can't both win.
  - **Email requests:** `email_requests`, the outbox ([email-outbox.md](../email-outbox.md#the-table)).

  `AppDbContext` derives from `IdentityUserContext`, so ASP.NET Core Identity's own role and claim tables are not in the model.

  `account_roles` and `role_permissions` hold ids: `Account` keeps its roles as `AccountRole` links and exposes `RoleIds`, `Role` keeps `RolePermission` links and exposes `PermissionIds`; neither has a navigation to the other aggregate ([domain-model.md](../domain-model.md#aggregates)). What an account's roles grant is read by a query (`IAccountsQueries`), never by loading roles.

## ASP.NET Core Identity

- **Registration.** `AddInfrastructure()` registers ASP.NET Core Identity (its private `AddIdentity()`), its options and the email-link token provider, so every host has it with the same rules; only the Api uses it today.
- **Store options.** `IdentityOptions.Stores` stays at its defaults: ASP.NET Core Identity reads it from the app's services while building the model, and the design-time factory and the other hosts don't have them, so changing it would give them a different model.
- **Email links:** `EmailLinkTokenProvider` is ASP.NET Core Identity's token provider for email confirmation and password reset (`AddDefaultTokenProviders` isn't used, so Data Protection doesn't make these tokens). It stores a SHA-256 hash per `AccountIdentity` and purpose in `email_link_tokens`; the lifetimes are in [security.md](../../../docs/security.md#accounts). Checking a link marks its row deleted, and ASP.NET Core Identity saves that in the same `SaveChanges` as the confirmation or the new password. So a handler must not save anything else in the same scope after an ASP.NET Core Identity call fails; otherwise a rejected password would use up the link.
- **No Data Protection key ring.** Nothing in the Api protects a payload with Data Protection. If a later feature needs it (cookies, antiforgery), it has to bring a persisted, encrypted key ring with it, decided in security.md first.

## Registration and confirmation

`AccountsEndpointModule` maps three endpoints under `/api/v1/auth`:

| Endpoint                   | Body                      | Response | Does                                                                                                                                                                                                 |
| -------------------------- | ------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST register`            | email, password, language | 202      | creates the `Account` and its unconfirmed `AccountIdentity` and requests `EmailConfirmation`; for a taken email, creates nothing and requests `AccountAlreadyExists`. Same empty response either way |
| `POST confirm-email`       | `{ id, token }`           | 204      | confirms the email through ASP.NET Core Identity; the link then stops working. Every failed link (unknown, wrong, expired, used) is 400 ProblemDetails `Accounts.InvalidEmailLink`                   |
| `POST resend-confirmation` | email                     | 202      | requests `EmailConfirmation` for the address without looking it up. Same empty response for any address                                                                                              |

A password that breaks the rules returns 400 ProblemDetails with field errors ([error-handling.md](../error-handling.md)).

## Sign-in, refresh and sign-out

`AccountsEndpointModule` maps three more endpoints under `/api/v1/auth` and `MeEndpointModule` maps `GET /api/v1/me`. Which endpoints need a token is in [architecture.md](../architecture.md#http-surface). The rules (lifetimes, reuse, lockout) are in [security.md](../../../docs/security.md#tokens).

| Endpoint         | Response                                             | Does                                                                                                                                                |
| ---------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST sign-in`   | 200 `{ accessToken, accessTokenExpiresAt }` + cookie | checks `{ email, password }`, starts a `Session` and issues both tokens                                                                             |
| `POST refresh`   | 200, same body, new cookie                           | exchanges the cookie's token for a new one (sliding: valid 7 days from issue) and re-reads the permissions. A failure is 401 and deletes the cookie |
| `POST sign-out`  | 204                                                  | deletes the session the cookie's token belongs to (used or not) and the cookie; succeeds even with no or an unknown cookie                          |
| `GET /api/v1/me` | 200 `{ email, language, roles, permissions }`        | the signed-in account's own details, read through `sub`; 401 without a valid token, 404 `Accounts.AccountNotFound` for an unknown account           |

- **Errors.** `Accounts.InvalidCredentials` 401, `Accounts.EmailNotConfirmed` 403 and `Accounts.LockedOut` 423 (the `Forbidden` and `Locked` categories, [error-handling.md](../error-handling.md#error-categories)); the 423 carries `Retry-After`, the whole seconds until the lockout ends, rounded up and at least 1, and CORS exposes it so the apps can read it; `Accounts.InvalidRefreshToken` 401 for a missing, unknown, expired or reused token.
- **Order of checks** (`IdentityPasswordSignIn`): an unknown email is hashed against a dummy password so the time matches, then invalid credentials; a locked-out account, which still verifies the password so the time matches; a wrong password, counted toward the lockout (the fifth failure locks but still answers invalid credentials); and only after the right password an unconfirmed email. A failure is counted with one atomic `ExecuteUpdate` on `identity_users` instead of `UserManager.AccessFailedAsync`, so parallel guesses can't drop increments: it adds one, at the limit locks and resets the count (limit and duration from `IdentityOptions`, time from the `TimeProvider`) and bumps `ConcurrencyStamp`. A right password resets the count only when it is above 0. Refresh doesn't check lockout, so a locked account's sessions keep working.
- **Access token.** `JwtAccessTokenIssuer` signs HS256 with `JsonWebTokenHandler`, valid 15 minutes. Claims: `sub` (account id), `sid` (session id), `jti`, `iat`, `exp` and one `permission` per permission the account's roles grant (`GetPermissionsAsync`). The Api validates issuer, audience, signature and lifetime with no clock skew, HS256 only, and keeps claims under their token names (`MapInboundClaims` off). The lifetime check reads the DI `TimeProvider`.
- **Settings.** `Jwt:SigningKey` (at least 64 characters) comes from the `jwt` item's `password` in 1Password through the Api's `.env.development`; `Jwt:Issuer` (`wattwise-api`) and `Jwt:Audience` (`wattwise-clients`) are names in the Api's `appsettings.json`. `JwtSettingsValidator` stops the host at start on a bad value.
- **Cookie.** `RefreshTokenCookie` (the only owner of the names and the rule) writes `__Secure-wattwise-refresh` for the frontend and `__Secure-wattwise-admin-refresh` for the admin app, so each app has its own session. A request whose `Origin` equals `Cors:AdminOrigin` (ordinal) uses the admin cookie; every other request (the frontend, no `Origin`, a non-browser client) and every request while the setting is blank uses the frontend one. The setting is described in [architecture.md](../architecture.md#http-surface). Both cookies: HttpOnly, Secure, `SameSite=Strict`, `Path=/api/v1/auth`, expiring with the token. The token is 32 random bytes, Base64Url-encoded; only its SHA-256 hash is stored.
- **Sessions.** `Session.Start` and `Rotate` take the time as an `Instant`. Rotating marks the presented token used and adds the next; a used token raises `RefreshTokenReusedException`, which the handler answers by deleting the session. A concurrent refresh with the same token loses on the `xmin` guard and is treated as reuse. Ended sessions are deleted with their token hashes. The device label is parsed from the User-Agent by `MyCSharp.HttpUserAgentParser` ("Firefox on Linux"; "Unknown device"; at most 100 characters); no IP address is stored.
- **Sign-in and the old cookie.** `SignInCommand` carries the refresh cookie the request sent. After the new session is saved, the session that cookie belongs to is deleted too (a second save through `SessionEnding`), but only when it is the same account's.
- **Purge.** `PurgeSessionsJob` (daily, 03:30 UTC) sends `PurgeExpiredSessionsCommand`: it deletes sessions with no unexpired token and expired token rows. A used but unexpired token is kept, so its reuse is still detected ([jobs.md](../jobs.md#job-classes)).
- **CORS and origin.** The `/auth` endpoints use the credentialed `AuthCorsPolicy`; the rest of the group uses `CorsPolicy`. An unsafe request from a foreign `Origin` is refused before the endpoint ([architecture.md](../architecture.md#http-surface)).

## Password reset and change

Three more endpoints under `/api/v1/auth`. The rules (lifetimes, lockout, what ends sessions) are in [security.md](../../../docs/security.md#accounts).

| Endpoint               | Body                               | Response                                             | Does                                                                                                                                                           |
| ---------------------- | ---------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST forgot-password` | email                              | 202                                                  | requests `PasswordReset` for the address without looking it up (the worker does); the same empty response for any address                                      |
| `POST reset-password`  | `{ id, token, newPassword }`       | 204                                                  | sets the password from the link, clears the lockout and ends every session; no session is left. A bad, used or expired link is 400 `Accounts.InvalidEmailLink` |
| `POST change-password` | `{ currentPassword, newPassword }` | 200 `{ accessToken, accessTokenExpiresAt }` + cookie | needs a Bearer token ([architecture.md](../architecture.md#http-surface)); ends every session, starts a new one for the caller                                 |

- **Errors.**
  - A new password that breaks the rules: 400 with field errors on `newPassword`. It is checked first, so a reset link still works afterwards.
  - `Accounts.InvalidEmailLink`: 400, for a bad, used or expired reset link.
  - `Accounts.InvalidCurrentPassword`: 400 with a field error on `currentPassword`. Not 401, because a client answers 401 with a refresh.
  - `Accounts.LockedOut`: 423, with `Retry-After` as under sign-in.
  - `Accounts.AccountNotFound`: 404.
  - `Accounts.PasswordChangeConflict`: 409, when another request changed the sign-in record or the sessions at the same moment ([error-handling.md](../error-handling.md#error-categories)).
  - An unexpected ASP.NET Core Identity rejection after the validators passed throws (a 500), and the runner's rollback keeps the link.
- **Order of checks for a change** (`IdentityPasswordChange.CheckCurrentAsync`, outside the runner): locked out, then the password. A wrong one is counted through `LockoutCounter`, the same atomic statement as sign-in, which commits at once; the right one resets the count. The identity is read without tracking and the hash is verified with the hasher, not `CheckPasswordAsync` (which saves when a hash needs upgrading).
- **The transaction.** `ResetPasswordCommandHandler` and the second half of `ChangePasswordCommandHandler` run in `ITransactionRunner` ([domain-model.md](../domain-model.md#persistence-ports)): ASP.NET Core Identity's one save, `IAccountSessions.EndAllAsync` (a bulk delete; the refresh tokens cascade) and, for a change, the new session's save are one transaction, so a failed step leaves the old password and the old sessions. `UserManager` saves the new hash with the staged removal of the reset link (a change) or of the used link (a reset).
- **Reset and lockout.** `IdentityPasswordReset` sets `LockoutEnd = null` and `AccessFailedCount = 0` on the tracked identity before `ResetPasswordAsync`, so they ride the same save.
- **Security stamp.** `Session.SecurityStamp` is the stamp the password was checked against (`PasswordCheck.Succeeded` carries it from sign-in; a change passes the new one). A reset or change replaces the stamp (`UserManager` does it when it sets a password; confirming an email, counting a failure and registration do not). `RefreshSessionCommandHandler` reads the current stamp through `IAccountsQueries.GetSecurityStampAsync` and, on a mismatch, deletes the session and answers `Accounts.InvalidRefreshToken`. Why this also closes the sign-in-versus-change race is in [security.md](../../../docs/security.md#sessions).
- **Rehash.** `IdentityPasswordSignIn` verifies with the hasher and not `CheckPasswordAsync`, which saves a new hash and replaces the stamp. On `SuccessRehashNeeded` it updates the hash and the concurrency stamp with one `ExecuteUpdate`: a rehash never rotates the security stamp. The update applies only while the row still holds the hash that was verified, so a change or reset that committed in between is never overwritten; otherwise the rehash is skipped and the next sign-in retries it.

## Sessions and devices

Three more endpoints under `/api/v1/auth`, all needing a Bearer token ([architecture.md](../architecture.md#http-surface)). The rules (what the user can do, when it takes effect) are in [security.md](../../../docs/security.md#sessions).

| Endpoint                   | Response                                                     | Does                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `GET sessions`             | 200 `[{ id, deviceLabel, signedInAt, lastUsedAt, current }]` | the account's listed sessions, newest `lastUsedAt` first; `current` marks the session in the token's `sid` claim (`GetSessionsAsync`) |
| `DELETE sessions/{id}`     | 204                                                          | ends one of the account's sessions with `IAccountSessions.EndAsync` (one statement, tokens cascade)                                   |
| `POST sign-out-everywhere` | 204                                                          | `IAccountSessions.EndAllAsync`, including the current session, and deletes the cookie                                                 |

- **Errors.** `Accounts.SessionNotFound`: 404, for an unknown id and for another account's session alike, so ids can't be probed.
- **Cookie.** Ending the current session (`id` equals `sid`) deletes the refresh cookie, like sign-out; ending another session, or a 404, leaves it.
- **List filter.** A session is listed only while it has an unexpired refresh token, the test `PurgeExpiredSessionsCommand` uses, so a dead session isn't shown before the purge runs ([security.md](../../../docs/security.md#sessions)).

## Admin role

The design (permissions in the token, the 15-minute window) is in [security.md](../../../docs/security.md#authorization).

- **Seed.** The `Initial` migration seeds, through `HasData` in the `Role`, `Permission` and `RolePermission` configurations, the `Admin` role, the `admin.access` permission and the row that grants it. Their ids are fixed (`RoleNames.AdminId`, `PermissionNames.AdminAccessId`), so every environment has the same ones.
- **Permission check.** `/api/v1/admin` is a route group mapped from every `IAdminEndpointModule` in DI and wrapped in `RequirePermission(PermissionNames.AdminAccess)` ([architecture.md](../architecture.md#http-surface)). `PermissionPolicies` holds one policy per permission, a `RequireClaim` on the token's `permission` claim; a new permission an endpoint checks must be added there. Endpoints never check role names. An anonymous call gets 401 and a signed-in account without the permission 403 `General.Forbidden`. No real admin endpoint exists yet; `TestAdminEndpointModule` in Api.IntegrationTests stands in ([testing.md](../testing.md)).
- **Commands.** `WattWise.Cli admin grant <email>` and `admin revoke <email>` ([development.md](../../../docs/development.md#accounts-for-development)) send `GrantAdminRoleCommand` and `RevokeAdminRoleCommand`. Both look the account up through `IAccountRoles.FindByEmailAsync` (the email is normalized like at sign-in) and need it to exist and have a confirmed email. The Cli connects as `cli` and switches to `owner` ([postgres.md](../../../deploy/docs/postgres.md)), which lets it write `account_roles` and delete sessions.

| Command  | Result                 | Does                                                                                                                                                                                   |
| -------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `grant`  | `RoleChange.Changed`   | inserts the `account_roles` row (`AddAsync`, `ON CONFLICT DO NOTHING`)                                                                                                                 |
| `grant`  | `RoleChange.Unchanged` | the account is already an admin: exit 0, "nothing changed"                                                                                                                             |
| `revoke` | `RoleChange.Changed`   | in one `ITransactionRunner` transaction, deletes the row (`RemoveAsync`) and ends every session (`IAccountSessions.EndAllAsync`), so the role is gone within one access-token lifetime |
| `revoke` | `RoleChange.Unchanged` | the account is not an admin: exit 0, "nothing changed", and no session is ended                                                                                                        |

- **Errors.** `Accounts.AccountNotFound` and `Accounts.EmailNotConfirmed`: the Cli prints `<code>: <description>` to stderr, exits 1 and changes nothing. An unexpected exception is logged and exits 1; Ctrl+C exits 130.
- **Security stamp.** Untouched: a role change is not a password change. A grant takes effect at the account's next refresh or sign-in, when the permission enters its token.

## Smoke accounts

`WattWise.Cli seed smoke-accounts` ([development.md](../../../docs/development.md#accounts-for-development)) keeps the two accounts the `/smoke-check` skill signs in with in a known state. The rule that it runs only in Development and keeps the credentials in 1Password is in [security.md](../../../docs/security.md#smoke-accounts).

- **Settings.** `SmokeAccounts:UserEmail`, `UserPassword`, `AdminEmail` and `AdminPassword`, filled from the 1Password item `smoke-accounts` through the Cli's `.env.development`.
- **Command.** For each account the Cli sends `SeedSmokeAccountCommand`; its handler asks `ISmokeAccounts.EnsureAsync` for the account, then sets the `Admin` role (the admin account has it, the user account does not) with the same `IAccountRoles` and `IAccountSessions` ports as the admin commands, in one `ITransactionRunner` transaction.
- **A new account** has its email confirmed, language `en` and no lockout, and no email is sent.
- **Changes only what differs.** An existing account is corrected to: confirmed email, the configured password, no lockout, the role above.

| Outcome     | Meaning                                        | Sessions                                                                                                                                                     |
| ----------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `created`   | the account did not exist                      | none to end                                                                                                                                                  |
| `changed`   | something differed and was corrected           | a changed password replaces the security stamp and ends every session; removing `Admin` from the user account ends every session; other corrections end none |
| `unchanged` | the account already was in the state asked for | none ended                                                                                                                                                   |

- **Output.** One line per account, `user: <outcome>` and `admin: <outcome>`; never an email or a password.
- **Errors.** Outside Development the Cli prints that the command runs only in Development and exits 1 before touching the database; the Infrastructure adapter refuses too ([security.md](../../../docs/security.md#smoke-accounts)).
