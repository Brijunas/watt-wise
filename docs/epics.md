# Watt-Wise — MVP Epics

Epics are ordered by dependency. Each one is expected to be delivered end to end (backend, frontend, tests) before the next starts, except where noted. `docs/product.md`, `docs/technical.md` and each project's own docs (e.g. `backend/docs/`) remain the source of truth; an epic never overrides them. When an epic's last story ships, the epic moves to [implemented.md](implemented.md).

## E3. Frontend foundation (frontend + admin + shared packages)

Creates the `frontend/` and `admin/` Vite React TypeScript apps in the workspace. Both PWAs booting with the app shell cached. MUI CSS-variables theme with light/dark/auto, choice in `localStorage` and applied before first paint. React Router shell, RTK Query store. Packages `@wattwise/ui`, `@wattwise/core`, `@wattwise/i18n` (LT/EN) and `@wattwise/api-client` with the `@rtk-query/codegen-openapi` pipeline from the API's OpenAPI document. Vitest + React Testing Library set up in every app and package. Extends `docs/development.md` with the app commands. Runs after E2 because the API client is generated from the real OpenAPI document.

### Stories

- **S3.1 Create the two Vite apps.** The developer runs `pnpm create vite` for `frontend/` and `admin/` with the React TypeScript template so the template matches the current release. Claude then adds them to the workspace, extends `tsconfig.base.json` and the shared ESLint/Prettier/Vitest configs, links the four `@wattwise/*` packages with `workspace:*` and adds one smoke component test each. Versions both apps share (React, MUI, Redux, i18next) go in a pnpm catalog in `pnpm-workspace.yaml` and are referenced as `catalog:`. Whenever an E3 story makes a package import a framework library (React, MUI, i18next, Redux), it adds that library to the package's `peerDependencies` and `devDependencies`; the apps own the real versions. Done: `pnpm --filter frontend dev/build/test` and the same for admin work.
- **S3.2 Pre-commit hook covers the apps.** Confirm the S1.2 hook (Husky + root `lint-staged.config.js`) lints and formats staged files in `frontend/` and `admin/`. Adjust the lint-staged globs or ESLint config only if app files are missed. Done: a commit with a lint error in either app is rejected locally.
- **S3.3 MUI theme with light/dark/auto.** `@wattwise/ui` exports the MUI CSS-variables theme with `colorSchemes`, a `ThemeProvider` wrapper and a mode switch using `useColorScheme`. The choice is stored in `localStorage` and an inline `<head>` script applies it before first paint. Both apps use it. Done: no flash on reload in either mode, mode switch covered by RTL tests.
- **S3.4 App shell and routing.** React Router in both apps with a mobile-first layout from `@wattwise/ui`: app bar, bottom navigation on phone and side navigation from the `md` breakpoint up, placeholder routes and a not-found page. Done: shell renders correctly at `xs` and `md` in component tests.
- **S3.5 i18n.** `@wattwise/i18n` sets up react-i18next with LT and EN resources, browser-language detection, a language switch component and a typed key convention. Both apps wrap with it. Done: switching language re-renders the shell, tests cover detection and switching.
- **S3.6 RTK Query store and generated API client.** `@wattwise/api-client` gets the `@rtk-query/codegen-openapi` config pointing at the API's OpenAPI document from S2.7, a `pnpm generate:api` root script and the committed output. No sample endpoint exists (S2.5 dropped it); which endpoint S3.6 uses is decided when S3.6 is planned. `@wattwise/core` provides the base query with the API URL from Vite env and the Redux store factory. Both apps mount the store and call that endpoint on a page. Done: regenerating produces no diff, the call renders data in both apps.
- **S3.7 Forms foundation.** react-hook-form with zod resolver, shared zod helpers in `@wattwise/core`, MUI-bound form fields in `@wattwise/ui` with error display and localized messages. One demo form under test. Done: validation errors show localized messages.
- **S3.8 PWA.** `vite-plugin-pwa` in both apps with manifest, icons, app-shell precaching and a network-only rule for `/api`. Update prompt when a new service worker is available. Done: Lighthouse reports installable, API requests are never served from cache.
- **S3.9 Vite env and config.** `.env.example` per app and env files for development/testing/staging/production with the API base URL, typed via `import.meta.env` declarations. Done: builds for each mode pick the correct API URL.
- **S3.10 App commands in development.md.** Extend `docs/development.md` with app dev/build/test, single test and API client regeneration commands. Done: each command executed and works.

## E4. Accounts and authentication

ASP.NET Core Identity with email and password: an account signs in only after confirming its email, and a forgotten password is reset through an emailed link. JWT access token plus a rotating refresh token in an httpOnly cookie; each sign-in is a session the user can see and end, one device at a time or everywhere at once ([security.md](security.md)). Transactional email over SMTP: Mailpit in Development and Testing, Brevo in Staging and Production ([technical.md](technical.md#cross-cutting)). `Admin` role guarding `/api/v1/admin`, granted with a `WattWise.Cli` command. Sign-up, sign-in, password and device pages with protected routes in the frontend; sign-in in the admin app. The account model leaves room for OAuth logins later without exposing them. Rate limiting on the auth endpoints and how the Hangfire dashboard is reached stay in E6. The backend stories (S4.1–S4.7) build on E2 and can start now; the app stories (S4.8–S4.10) need E3's routing, forms, i18n and generated API client.

### Stories

- **S4.1 Identity and the account model.** ASP.NET Core Identity in `WattWise.Infrastructure` on `AppDbContext`, its tables in the `app` schema, with the account rules in [security.md](security.md#accounts): email as the unique sign-in name, compared without regard to case; a confirmed email required to sign in; the password rules; the lockout. Each account also keeps a preferred language (LT or EN) for its emails. Identity's external-login table stays in the model so OAuth can be added later, but nothing uses it. The Data Protection keys behind email links are stored in the database. One migration, applied by `WattWise.Cli migrate`. The `api` role already reads and writes every `app` table ([postgres.md](../deploy/docs/postgres.md#roles)), so no grant changes. Done: `WattWise.Cli migrate` applies the migration to a fresh and to an already-migrated database; Infrastructure integration tests prove that a password shorter than 14 characters or missing any required character class is rejected, that a second account whose email differs only in case is rejected, that the fifth failed sign-in in a row locks the account for 15 minutes, and that an email token issued before a host restart is still valid after it; `dotnet ef migrations has-pending-model-changes` passes.
- **S4.2 Email sending.** An Application port for sending email, implemented in Infrastructure over SMTP with MailKit. Its settings are a validated `Smtp` section filled from 1Password through the Api's `.env.<environment>` file; the host stops at start when one is missing, like `Database`. Messages come from LT and EN templates (plain text and HTML), picked by the account's preferred language. The Development compose stack gets a Mailpit container whose SMTP and web addresses come from new 1Password items; `deploy/docs/`, `docs/setup.md` and `docs/development.md` say how to start it and where to read the caught emails. Mailpit for Testing and the Brevo account for Staging and Production are set up in E5. Done: an Infrastructure integration test sends a message through the port to a Mailpit Testcontainer and reads it back through Mailpit's API with the right recipient, subject and language; the Api stops at start when an `Smtp` setting is missing; an email sent by the Development Api shows up in Mailpit's web UI.
- **S4.3 Registration and email confirmation.** Register (email, password, language), confirm-email and resend-confirmation endpoints under `/api/v1/auth`. Registering creates an unconfirmed account and emails a link to the frontend's confirmation page. Neither registering nor resending reveals whether an email already has an account: both give the same response either way, and the owner of an existing account gets an email saying someone tried to register with it instead of a link. Done: Api integration tests, reading the emails from a test double, prove that following the link confirms the account; that a second use of the link, an altered link and another account's link all fail; that registering a taken email returns the same status and body as a new one and creates no second account; that a password breaking the rules returns 400 ProblemDetails with field errors; and that the email comes in the language sent at registration.
- **S4.4 Sign-in, refresh and sign-out.** Sign-in, refresh and sign-out endpoints under `/api/v1/auth`, following the flow in [technical.md](technical.md#backend) and the token rules in [security.md](security.md#tokens), plus `GET /api/v1/me` with the signed-in account's email, language and roles. JWT bearer authentication on the `/api/v1` group, with the signing key from 1Password through the Api's `.env.<environment>` file; the auth endpoints get a CORS policy that allows credentials, the rest of `/api/v1` keeps the S2.7 policy. Each sign-in starts a session that records what [security.md](security.md#sessions) lists (device label, sign-in time, last use), and sign-out ends it. Wrong credentials, an unconfirmed email and a locked-out account each have their own error code, and the unconfirmed code is returned only after the password is checked. Done: Api integration tests prove that `/me` answers with a valid access token and returns 401 ProblemDetails with none, an expired one or a tampered one; that refresh returns a new access token and cookie, and replaying the old cookie fails and ends the session, so the new cookie fails too; that after sign-out the cookie no longer refreshes; that the cookie is httpOnly, Secure, `SameSite=Strict` and limited to the auth path; that with a controlled clock the access token expires after 15 minutes and the refresh token after 7 days; and that a preflight to an auth endpoint allows credentials for the configured origins and no others.
- **S4.5 Password reset and change.** Forgot-password (emails a reset link to the frontend's reset page), reset-password (sets a new password from a valid link) and change-password for a signed-in account (needs the current password), under `/api/v1/auth`. Forgot-password gives the same response whether or not the email has an account. A reset or a change ends every session of the account. Done: Api integration tests prove that a reset link sets the new password and the old one stops working; that a link fails on its second use and after 1 hour; that an unknown email gets the same response and no email is sent; that the new password must follow the rules; that every refresh token issued before a reset or a change is rejected afterwards; and that a change with the wrong current password fails and leaves the password as it was.
- **S4.6 Sessions and devices.** Endpoints under `/api/v1/auth` for the signed-in account to list its sessions (device label, sign-in time, last use, the current one marked), end one of them, and sign out everywhere, which ends every session including the current one ([security.md](security.md#sessions)). Ending a session stops its refresh token at once; access tokens already issued run out within 15 minutes, as security.md records. Done: Api integration tests prove that two sign-ins show as two sessions with their labels and times and only the caller's marked current; that ending the other session makes its refresh fail while the current one keeps working; that ending the current session works like sign-out; that signing out everywhere makes every session's refresh fail, the current one included, and clears the cookie; that ending another account's session returns the same 404 ProblemDetails as an unknown id and leaves it working; and that a session ended by refresh-token reuse is no longer listed.
- **S4.7 Admin role.** The `Admin` role and an `/api/v1/admin` route group that requires it. The `Forbidden` error category (403) added to `ErrorTypeMapping` and [error-handling.md](../backend/docs/error-handling.md#error-categories). `WattWise.Cli admin grant <email>` and `admin revoke <email>` give the role to an existing confirmed account and take it away; revoking also ends every session of the account, so the role is gone within one access-token lifetime ([security.md](security.md#authorization)). The commands go into `docs/development.md`. No real admin endpoint exists yet, so a test endpoint module in Api.IntegrationTests stands in, as in S2.6. Done: Api integration tests prove that the test admin endpoint returns 401 ProblemDetails to an anonymous call, 403 ProblemDetails to a signed-in non-admin and 200 to an admin; integration tests of the grant and revoke use cases prove that an unknown or unconfirmed email fails and changes nothing, and that after a revoke the account's sessions no longer refresh; `admin grant` run against the Development database lets that account call the admin group.
- **S4.8 Token handling in the clients.** `@wattwise/core` gets the session state: the access token kept in memory only, a refresh when the app starts so the cookie restores the session after a reload, and a base query that on a 401 refreshes once and retries, with requests failing together sharing one refresh; a failed refresh signs out. Requests to the auth endpoints send credentials. `@wattwise/api-client` regenerated with E4's endpoints. Done: Vitest tests prove that a start with a valid cookie restores the session without showing sign-in; that two requests failing with 401 at once cause one refresh and are both retried; that a failed refresh clears the session; and that no token is ever written to `localStorage` or `sessionStorage`; `pnpm generate:api` produces no diff.
- **S4.9 Frontend account pages.** In `frontend/`: sign-up, "check your email", the confirmation page the email links to, sign-in, forgot password, reset password, change password, a devices page (the sessions from S4.6, ending one, signing out everywhere) and sign-out, built on S3.7's forms in LT and EN; sign-up sends the current UI language. Each error code from S4.3–S4.6 shows a localized message: an unconfirmed email offers to resend the link, a locked-out account says when to try again. Protected routes send a signed-out user to sign-in and back to the page they asked for afterwards. Done: RTL tests cover each page's success and error states; ending the current session or signing out everywhere on the devices page sends the user to sign-in; a protected route redirects to sign-in and returns to the requested page after it; every page renders at `xs` and `md` in both languages.
- **S4.10 Admin app sign-in.** `admin/` gets sign-in and sign-out on `@wattwise/core`, and every route requires an account with the `Admin` role (from `/me`). A signed-in account without it sees a no-access page and is signed out. The admin app has no sign-up or reset pages; its forgot-password link opens the frontend's page. Done: RTL tests prove that an anonymous visit shows sign-in, a non-admin sees the no-access page and ends signed out, an admin reaches the shell, and an admin's session survives a reload.

## E5. Deployment and CI/CD

Dockerfiles for api, jobs, cli, frontend and admin. Docker Compose files for Testing, Staging and Production, with a one-shot `cli migrate` service that api and jobs wait for (`depends_on: condition: service_completed_successfully`), and an admin-run `bootstrap.sql` step per database. 1Password vaults `Watt Wise Testing`, `Watt Wise Staging` and `Watt Wise Production`, one service account per environment. `.env.testing`, `.env.staging` and `.env.production` reference files per backend project. Email: Mailpit in the Testing stack, and a Brevo account with its SMTP settings in the Staging and Production vaults. cloudflared configuration, no open ports. 1Password `op run` / `op inject` for secrets and `deploy/.env.example` referencing item paths. GitHub Actions: PR workflow builds, lints and tests all apps and fails on `dotnet ef migrations has-pending-model-changes`; main workflow pushes images to GHCR and deploys over SSH. Renovate opens dependency update PRs (npm, NuGet, Docker images, GitHub Actions, `mise.toml`) with a one-day minimum release age and grouped related packages, checked by the PR workflow. From here on every epic ships to staging.

## E6. Observability and hardening

Closes the gaps left open on purpose before real users arrive. Limits: rate limiting on the auth endpoints, an upload rate and size limit ready for E7 to apply, security headers and a narrowed CORS policy ([security.md](security.md#transport-and-limits)). The Hangfire dashboard stays off the internet and is reached over SSH. Operations: security events in the logs, a trace per job run, Grafana dashboards, a runbook of queries and email alerts; a daily encrypted `pg_dump` per deployed stack and a restore drill performed once ([technical.md](technical.md#hosting-and-operations)). Runs after E4, whose endpoints, sessions and `Admin` role it protects, and after E5, whose deployed stacks, tunnel, app containers, telemetry receiver and Brevo account it configures.

### Stories

- **S6.1 Rate and size limits.** Rate limiting in the Api with the limits and counters in [security.md](security.md#transport-and-limits): one per-IP counter shared by all `/api/v1/auth` endpoints and a second, tighter one shared by the endpoints that send email, plus a named upload policy (per account) and an upload body-size limit that no endpoint uses yet; E7's upload endpoint applies both. The client address is the connection's own address, except when the request arrives from the tunnel container: then it is taken from the `CF-Connecting-IP` header. The tunnel's address is a setting from 1Password, which needs E5's compose file to give `cloudflared` a fixed address or subnet; unset, as in Development, the header is never read. The address is never stored or logged. A rejection is not an `ErrorType`: no handler returns it, so 429 and 413 are responses the framework produces, with the `General.<ReasonPhrase>` code of [error-handling.md](../backend/docs/error-handling.md#the-contract-clients-see), which gets a line for both. The rate-limiting meter is added to the collected meters ([observability.md](../backend/docs/observability.md#shared-setup)), and how the limits are wired goes into [architecture.md](../backend/docs/architecture.md#http-surface). Counters live in the Api's memory, which is enough for one instance. A test endpoint module in Api.IntegrationTests stands in for the upload endpoint, as in S4.7. Done: Api integration tests that control time (a controlled clock, or windows shortened through test settings) prove that after 10 requests from one address spread over two auth endpoints the 11th within the minute, to a third, returns 429 ProblemDetails with `Retry-After` and code `General.TooManyRequests` while another address still gets through, and that the counter is free again after the minute; that after 5 email-sending requests from one address spread over register and forgot-password the 6th within the hour returns 429 and sends no email; that the 21st upload within an hour by one account returns 429 while another account's upload passes; that a 5 MB + 1 byte body returns 413 ProblemDetails and a 5 MB one passes; that `CF-Connecting-IP` is used when the request comes from the configured tunnel address and ignored when it comes from anywhere else; that no log event or span attribute of a request contains the client address; and that `/health` and the rest of `/api/v1` are not limited.
- **S6.2 Security headers.** The headers in [security.md](security.md#transport-and-limits) on every response of the Api, the Jobs host and the two app containers from E5, set in the server each one runs on. Decided when the story is planned and recorded in security.md: the `Strict-Transport-Security` value, the looser Content-Security-Policy that the Scalar page needs outside Production and the Hangfire dashboard needs on the Jobs host, and how MUI's injected styles are allowed in the apps without opening scripts to `unsafe-inline`. The apps' policy allows inline scripts only by hash (the theme script from S3.3), the service worker from S3.8 and calls to the API origin of that environment. Done: Api and Jobs integration tests prove that a 200, a 404 and a 500 response each carry all four headers, and that only the Scalar and dashboard paths get the looser policy; a test in each app builds it and fails when any inline script in the built `index.html` has no matching hash in the policy; in Development `/scalar` and `/hangfire` load and work with no Content-Security-Policy violation in the browser console; on Staging both apps load, switch theme, sign in and install as PWAs with no violation in the console, and a page that frames either app is refused.
- **S6.3 CORS hardening.** The S2.7 policy is loose on purpose. Narrow it to what E4's endpoints really use: only the methods and request headers that some `/api/v1` endpoint needs, credentials only on the auth endpoints (S4.4), and the preflight cache time reviewed and written down. The allowed origins stay the frontend and admin URLs of each environment from 1Password, and the story checks each deployed environment's `.env.<environment>` maps exactly those two. The outcome replaces the CORS entry in [architecture.md](../backend/docs/architecture.md#http-surface), and the "E6 narrows it" note in [security.md](security.md#transport-and-limits) goes. Done: an Api integration test reads the mapped `/api/v1` endpoints and fails when the policy allows a method no endpoint uses or misses one an endpoint needs; tests prove that a preflight from an origin outside the list, or asking for a header outside the list, gets no CORS headers; that a non-auth endpoint never answers with `Access-Control-Allow-Credentials`; and that no response carries a wildcard origin.
- **S6.4 Hangfire dashboard off the internet.** The dashboard is never reachable from the internet; a person with SSH access to the server opens it through an SSH tunnel ([security.md](security.md#authorization)). In each deployed stack the Jobs container's port is published only on the server's loopback address, the tunnel has no route to the Jobs host, and no other container can open the dashboard. Inside a container Hangfire's local-requests-only filter sees Docker's gateway address, not loopback, for a request that came through the published port, so which addresses the dashboard accepts becomes a validated Jobs setting from 1Password, empty meaning loopback only as today. The gateway address is stable only if E5's compose file fixes the network's subnet, as for `cloudflared` in S6.1; the filter that reads it replaces Hangfire's default and is described in [jobs.md](../backend/docs/jobs.md#dashboard). Development keeps opening it directly on the loopback address. The SSH command goes into `docs/development.md`. Done: Jobs integration tests prove that the dashboard answers 200 to loopback and to a configured address, and 401 to any other address and to a request with no remote address; that a forwarded-address header doesn't change the answer; and that a malformed setting stops the host at start; on Staging the dashboard opens through the SSH tunnel, a request to it from the `api` container gets 401, and no hostname of the Cloudflare Tunnel leads to the Jobs host.
- **S6.5 Security event logs.** One structured log event, each with its own stable event name, for: a failed sign-in, an account lockout, a refresh token presented twice, a rate-limit rejection, a password reset or change, `admin grant` and `admin revoke`. Events identify the account by its id only: no email address, IP address, token or password appears in any of them, and a failed sign-in for an unknown email carries no identifier at all. The failed sign-in that locks an account writes both its own event and the lockout event. The list of events and their fields goes into [observability.md](../backend/docs/observability.md). Done: integration tests capture the log events through a registered sink, as the S2.8 tests do, and prove that each case above writes its event exactly once with its name and the account id where one exists; that the fifth failed sign-in writes one failed-sign-in and one lockout event; that a successful sign-in writes none of them; and that across all of them no property or rendered message contains the email, the client address, a token or a password used in the test.
- **S6.6 A trace per job run.** A Hangfire server filter in `WattWise.Jobs` starts one span per job run from a `WattWise.Jobs` activity source, named after the job, with the job id and the recurring job id as tags and status Error when the job throws. The run's database calls become its children, so `ParentlessDatabaseSpanFilter` keeps them, while Hangfire's own polling stays dropped ([observability.md](../backend/docs/observability.md#correlation)). A `WattWise.Jobs` meter counts job runs by job and outcome and records their duration, for S6.9's dashboard. The "Not yet" section of [jobs.md](../backend/docs/jobs.md#not-yet) is replaced by a description of both. Done: Jobs integration tests prove that triggering a job that queries the database records one root span for the run with the query's span as its child, and that the log lines written inside the job carry that trace id; that a throwing job's span has status Error; that a succeeded and a failed run each add one to the counter under their outcome; and that an idle server records no spans.
- **S6.7 Database dumps.** The trigger: the `backup` role exists since S2.3 but nothing uses it, and a file copy of a running data folder is not a consistent backup ([technical.md](technical.md#hosting-and-operations)). The Testing, Staging and Production compose stacks get a service, on the pinned PostgreSQL image ([postgres.md](../deploy/docs/postgres.md#version)), that once a day runs `pg_dump` of `wattwise` as `backup` with the password from that vault's `postgres-backup` item, encrypts the compressed custom-format dump with a key from a new 1Password item, writes it under a timestamped name and then deletes all but the newest 2 ([security.md](security.md#elsewhere)). A dump gets its final name only when both steps succeed, so a failed run never replaces a good dump or counts toward the 2. The folder is readable only by the service's user and root. The encryption tool, and how a run's outcome reaches the telemetry receiver for S6.10's alert (it depends on whether E5 ships container logs), are decided when the story is planned and recorded in postgres.md. The developer names the folder that the server's backup setup already copies, confirms the dumps arrive in the off-server copy, and gives that setup's retention period for security.md. A "Backups" section in postgres.md describes the schedule, the folder, the retention and the key; the command to run a dump by hand goes into `docs/development.md` only. Done: a test script run against a throwaway PostgreSQL container proves that three runs leave exactly the 2 newest dumps; that a run with a wrong password leaves the existing dumps untouched, writes no partial file and exits non-zero; that a dump can't be read by `pg_restore --list` as stored and can after decrypting with the key; on Staging a dump from the scheduled run is in the folder the next day and in the off-server copy, and no other user on the server can read it.
- **S6.8 Restore drill.** A backup counts only once a restore from it has worked. [postgres.md](../deploy/docs/postgres.md) gets a "Restore" section with two procedures. The drill: stop Api and Jobs on Staging, run a dump by hand (S6.7's command), record the row count of every table, start them again, wait for that dump to reach the off-server copy, take it back from there, decrypt it, restore it as `admin` into a scratch database next to `wattwise`, check it and drop the scratch database. A real restore over `wattwise`: run the bootstrap first, since roles are not in a dump, restore, and run the bootstrap again for the database-level settings; table privileges come from the dump itself, because the bootstrap doesn't grant on existing tables ([postgres.md](../deploy/docs/postgres.md#schemas-and-privileges)). The developer performs the drill on Staging once, with Claude writing the steps and fixing them where the drill shows they are wrong. Done: the restored dump came back from the off-server copy, not from the local folder; in the scratch database every table of `app`, `hangfire` and `migrations` has the row count recorded at dump time and the same owner as in the source; `api` and `jobs` have the same table privileges there as in the source; the scratch database is dropped afterwards; and the section records the date of the drill, how long the restore took and the dump's size.
- **S6.9 Dashboards and query runbook.** Grafana dashboards kept as provisioning files under `deploy/`, loaded by the Development LGTM container and by the receiver E5 chose for the deployed environments; if that receiver is not Grafana, this story and S6.10 are replanned before they start. One dashboard for the Api (request rate, 4xx and 5xx rate, latency percentiles per route, rate-limit rejections from S6.1's meter) and one for jobs and the database (job runs, failures and duration from S6.6's meter, Npgsql connections and command duration). A new `deploy/docs/runbook.md` lists the saved queries: find a request by the `traceId` of a ProblemDetails, errors per service, slowest requests, each security event from S6.5, a job run's trace; "Finding a request" moves there from [lgtm.md](../deploy/docs/lgtm.md). Done: `docker compose … up` on a fresh volume shows both dashboards with no manual import, and after a few requests, a rate-limit rejection and a triggered job every panel shows data; every query in the runbook has been run against Development and returns the event it describes; on Staging both dashboards show that environment's data.
- **S6.10 Alerts.** Three alert rules as provisioning files next to S6.9's dashboards: the Api's 5xx rate above a threshold, the Api or the Jobs host unhealthy or silent, and no successful database dump (S6.7) in the last 26 hours. The Jobs host gets the same `/health` report as the Api, with the database check ([jobs.md](../backend/docs/jobs.md#host-setup)). Grafana can't probe hosts that listen on a developer's loopback address, so how each host's health reaches the receiver (for example a metric the hosts export over OTLP, alerting on its value and on no data) is decided when the story is planned and recorded in [observability.md](../backend/docs/observability.md). The dump rule is loaded only in the deployed environments, since Development has no dump service. Alerts are emailed to the address in a new 1Password item through the environment's SMTP settings: Mailpit in Development and Testing, Brevo in Staging and Production. They share Brevo's 300 emails a day with account emails ([technical.md](technical.md#cross-cutting)), so the rules group alerts and repeat a firing one no more than every few hours. The thresholds, the grouping and the repeat interval are chosen when the story is planned and written into `deploy/docs/runbook.md`, with what to do for each alert. Done: a Jobs integration test proves `/health` answers 200 with the database up and 503 with it down, without exception text; in Development, stopping the `postgres` container makes the health alert fire for both hosts in one email that arrives in Mailpit, and starting it again resolves it; stopping the Jobs host alone fires it for Jobs only; on Staging a test alert reaches the real inbox through Brevo, and the dump alert fires when its window is temporarily set shorter than the age of the newest dump and resolves with the real window.

## E7. Consumption objects and CSV import

Consumption object CRUD, any number of objects per account. ESO CSV parser targeting exactly what Mano ESO exports, Europe/Vilnius interpreted and stored as UTC; how DST days appear in the export is still open, see [known-issues.md](known-issues.md#eso-csv-format-around-dst-changes-is-unknown). Hourly rows keyed by `(consumption_object_id, hour_utc)` with upsert so repeated uploads merge. The CSV itself is discarded after import. Upload UI with clear validation feedback. The upload endpoint applies the upload rate and size limits built in S6.1.

## E8. Consumption visualization

Rich, filterable chart of consumption at hourly, daily and monthly resolution using MUI X Charts. Period selection and summary statistics. Mobile-first.

## E9. Grid plan domain

ESO grid plan model with its pricing components. Household parameters (contracted power, phases) if the ESO tariff structure requires them; this epic resolves that open question in `docs/product.md`. Draft/published lifecycle. Grid plan ingestion job from the ESO source writing drafts. Admin UI to create, edit, publish and retire grid plans. Public catalog page for grid plans.

## E10. Provider plan domain

Supplier plan model built from typed pricing components: fixed rate, time-of-use 2- and 4-zone, spot margin, monthly fee, hybrid. Compatibility rules with grid plans so only valid pairs are offered. Draft/published lifecycle. Per-provider fetchers or scrapers, source chosen per provider, writing drafts with change detection so re-runs do not duplicate. Admin review, edit and publish UI. Public catalog page for supplier plans.

## E11. Spot price ingestion

Hangfire job fetching Nord Pool LT day-ahead hourly prices, ENTSO-E primary with Nord Pool or Litgrid open data as fallback. Storage as `(hour_utc, price_eur_mwh)`. Backfill covering at least the range users can upload, gap detection and refill. Admin visibility of price coverage.

## E12. Current plans baseline

User selects their current grid plan and current supplier plan from the catalog, or enters custom pricing when their plan is not listed. Stored per consumption object and editable.

## E13. Estimated cost engine

Pure Domain engine that estimates what a plan would have cost over a period from hourly consumption, spot prices and pricing components. It is explicitly an estimate, not actual billing: no generation, net metering or invoice reconciliation in MVP, but the inputs are shaped so those can be added later. Time-of-use zones evaluated in local time with correct 23- and 25-hour DST days. Monthly and yearly aggregation. Golden-case unit tests in `Domain.Tests`.

## E14. Comparison and ranking

Query that runs the engine over all published grid plans, supplier plans and valid grid+supplier combinations for the selected period and cost basis, ranks by estimated cost and computes estimated savings versus the baseline. Results UI with period and basis controls, defaulting to the last year and monthly basis, with the note that spot results are a backtest estimate, not a forecast.

## E15. GDPR: export and delete

Full data export bundle for an account. Full account deletion cascading through consumption objects, consumption rows and baselines. Confirmation flows in the UI.

## Out of scope for MVP

Prosumer support, multiple consumption objects in the UI, OAuth sign-in and price alerts are non-goals per `docs/product.md` and have no epics.
