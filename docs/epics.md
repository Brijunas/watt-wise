# Watt-Wise — MVP Epics

Epics are ordered by dependency. Each one is expected to be delivered end to end (backend, frontend, tests) before the next starts, except where noted. `docs/product.md`, `docs/technical.md` and each project's own docs (`backend/docs/`, `frontend/docs/`, `deploy/docs/`) remain the source of truth; an epic never overrides them. When an epic's last story ships, the epic moves to [implemented.md](implemented.md).

## E5A. Visual identity

Brings both apps to the look in [style.md](../frontend/docs/style.md) and the shell in [layout.md](../frontend/docs/layout.md): the logo palette in light and dark, a glow the user can switch off, Red Hat Display everywhere, the user's logo, and Material 3 breakpoints with a rail and capped content. E5A builds the MUI theme in `@wattwise/ui` from style.md and moves both apps onto it, following MUI's own guides ([theme.md](../frontend/docs/theme.md#mui): tokens and variants in the theme, nothing styled per component); every story writes MUI v9 code ([theme.md](../frontend/docs/theme.md#mui-v9)), so the code each story touches moves to v9 as it is rewritten. It comes before E5B so the first deployed release carries the brand, and before E7 so new screens start in it. The results, chart and state patterns in layout.md are built by the epics that own those screens (E8, E14).

## E5B. Deployment and CI/CD

Ships Watt-Wise to saturn. Docker images for api, jobs, cli, frontend and admin, built and signed by GitHub Actions. Testing, Staging and Production as Compose stacks on saturn, each with its own PostgreSQL, 1Password vault, Cloudflare Tunnel and subdomains, and one shared Grafana LGTM for their logs, traces and metrics. Deploys are pulled: GitHub Actions moves a registry tag (`dev` → Testing, `main` → Staging, a manual swap of Staging and Production), and an agent on saturn verifies the signatures and deploys. Nothing connects into saturn, and the repo says nothing about it beyond its name. The flow is under "Hosting and operations" in [technical.md](technical.md#hosting-and-operations), the rules under "Deployment" and "CI and contributions" in [security.md](security.md#deployment). Renovate opens the dependency update PRs. It comes after E4 because the stacks need E4's SMTP and JWT settings, and after E3 because the frontend and admin images build its apps; S5B.1, S5B.3 and S5B.6 don't need E3 and can start earlier. From here on every merge to `main` ships to Staging.

### Stories

- **S5B.1 Backend images.** Dockerfiles for `WattWise.Api`, `WattWise.Jobs` and `WattWise.Cli`, built from the repo root with a `.dockerignore`: the SDK only in the build stage, a runtime image without it, a non-root user. The images hold no settings or secrets: no `.env*` file and no `appsettings.*.local.json`; everything arrives as environment variables ([technical.md](technical.md#cross-cutting)). The Cli image's entry point is the Cli, so `docker run <image> migrate` migrates. The Jobs host gets the same `/health` with a database check as the Api ([jobs.md](../backend/docs/jobs.md) records it), and both images get a container health check on it. How the images are built and run goes into a new `deploy/docs/images.md`, the build commands into `docs/development.md`. Done: each image builds from the repo root; `docker image inspect` shows a non-root user; the runtime images contain no .NET SDK and no `.env*` file; the Cli image migrates the Development database, and the Api and Jobs images then start against it and report healthy, with their settings passed by `op run` from the existing `.env.development` files; a Jobs integration test covers its `/health` like the Api's.
- **S5B.2 Frontend and admin images.** One image each for `frontend/` and `admin/`: the Vite build in a Node stage, served by `nginxinc/nginx-unprivileged` as a non-root user ([technical.md](technical.md#hosting-and-operations)). A path that isn't a file falls back to `index.html` for the router, except under the hashed assets folder, where a missing file is a 404. Hashed assets are cached for a year as immutable; `index.html`, the service worker and the manifest are never cached, so a release reaches users on their next visit through S3.8's update prompt. The image must run unchanged in Staging and then Production: at container start nginx renders `/config.js` from the container's `API_BASE_URL` (and, in the admin image, `FRONTEND_URL`: the frontend's origin, for the forgot-password link) with its envsubst templates, served `no-cache`, and a missing `/config.js` is a 404, not `index.html` ([frontend/docs/architecture.md](../frontend/docs/architecture.md#runtime-config)); the non-root container needs a writable place for the rendered file. S5B.2 makes `social-card.png` (1200×630) composed from `frontend/public/logo-lockup-dark.png` on `#05060E` by a Codex worker (image work is never done by Claude agents), with no new artwork. The apps' `index.html` also gets the social card tags (`og:*`, and `twitter:card` with `social-card.png`) with an absolute URL, which needs each app's public URL; where that setting comes from is decided when the story is planned. The nginx rules go into `deploy/docs/images.md`. Done: each image builds from the repo root; against a running container, a deep link to a client route returns `index.html` with 200, a missing hashed asset returns 404, a hashed asset carries `Cache-Control: public, max-age=31536000, immutable`, and `index.html` and the service worker carry `no-cache`; the container runs as a non-root user; an image built once reaches Staging's API when run with Staging's settings and Production's with Production's, and a container started without `API_BASE_URL` (or, for admin, `FRONTEND_URL`) stops instead of serving.
- **S5B.3 Pull request workflow.** A workflow in `.github/workflows/` on every pull request to `main`: the tools from `mise.toml`, the checks in [development.md](development.md#checks), `dotnet ef migrations has-pending-model-changes`, `pnpm generate:api` followed by a check that it left no diff (the committed OpenAPI document and API client are current), a Betterleaks scan of the PR's commits (the local hook can be skipped, CI can't), zizmor over the workflows, and a build of every image that exists (S5B.1, S5B.2) without pushing. It follows "CI and contributions" in [security.md](security.md#ci-and-contributions): `pull_request`, never `pull_request_target`; no secrets; each job's `permissions` set explicitly; every action pinned to a full commit SHA. The developer enables GitHub Actions and, in the repository settings, requires SHA-pinned actions, stops Actions from creating or approving pull requests, keeps fork workflows waiting for approval for all external contributors, and adds the check to `main`'s ruleset, which already requires signed commits and pull requests. `.github/workflows/README.md` and development.md say what CI runs. Done: throwaway PRs each fail the check and can't be merged when they add an ESLint error, an unformatted file, a type error, a failing JS or .NET test, a backend build warning, a model change without a migration, a fake secret in a commit, a Dockerfile that no longer builds, an action referenced by tag instead of SHA, or a workflow zizmor flags; a clean PR passes and squash-merges as a commit GitHub shows as verified; a new push to a PR cancels its run still in progress.
- **S5B.4 Image publishing and signing.** A workflow that, on every push to `main` and `dev`, builds the five images, pushes them to GitHub Container Registry tagged with the commit SHA, with the OCI labels for the source repository and revision, and signs each by digest with keyless cosign ([security.md](security.md#deployment)). Only the signing job gets `id-token: write`, and only the push job package write. The packages are public like the repository, since the images hold nothing secret (S5B.1). How to verify an image by hand goes into `deploy/docs/images.md`. Done: after a push to `dev`, the five images for that SHA are in GHCR, pull without credentials and carry that SHA as their revision label; `cosign verify` with this workflow's identity on `refs/heads/dev` accepts them, and with the identity on `refs/heads/main` rejects them; the same holds the other way round for a push to `main`; an image pushed by hand or from any other workflow fails both; a pull request never pushes or signs an image; a second push of the same SHA leaves the published images as they were.
- **S5B.5 Renovate.** The developer installs the Mend-hosted Renovate app on the repo; Claude adds `renovate.json` with the policy in [technical.md](technical.md#repository): npm through pnpm, NuGet through `backend/Directory.Packages.props`, the Docker images in the Dockerfiles and compose files, GitHub Actions and `mise.toml`; a one-day minimum release age; related packages grouped (e.g. React, MUI, typescript-eslint, OpenTelemetry, EF Core with Npgsql); majors in their own PRs; actions pinned to commit SHAs with the version as a comment (`helpers:pinGitHubActionDigests`). It follows [known-issues.md](known-issues.md) and [postgres.md](../deploy/docs/postgres.md#version): the `typescript` alias stays on 6, the .NET SDK pin in `mise.toml` and `global.json` moves together, and PostgreSQL never gets a major bump, while its tag in the compose files and in `PostgresContainerFixture` changes in one PR. "Updating dependencies" in development.md says how Renovate's PRs are handled. Done: `renovate-config-validator` accepts `renovate.json`; Renovate's dependency dashboard lists dependencies from every manager above; its first PRs run the S5B.3 check, and its action updates keep SHA pins; no PR proposes the `typescript` alias at 7, a PostgreSQL major, or a release younger than a day.
- **S5B.6 Shared Grafana LGTM on saturn.** A Compose project on saturn running `grafana/otel-lgtm`, the image Development uses ([lgtm.md](../deploy/docs/lgtm.md)). The three stacks reach its OTLP receiver over a shared Docker network; the receiver publishes no port. Grafana publishes only on saturn's loopback, at a port from a new 1Password item (which vault holds it is decided when the story is planned), with the same anonymous access as in Development ([security.md](security.md#deployment)). Its data lives in a volume. The developer starts and updates it on saturn; lgtm.md gets a section with those commands, and how to reach saturn goes only into the private runbook. Done: the project comes up healthy with `up -d --wait`; Grafana answers on saturn's loopback and on no other address; the OTLP port is reachable from a container on the shared network and not from saturn's host network or the internet; the data survives `docker compose down` and `up`.
- **S5B.7 Testing stack.** Testing runs on saturn from `deploy/`:
  - a Compose file for Testing with PostgreSQL 18.6 (the Development hardening flags, no published port); a one-shot `cli` service running `migrate` that `api` and `jobs` wait for (`depends_on: condition: service_completed_successfully`); `api`, `jobs`, `frontend` and `admin` by image digest; Mailpit with its web UI on saturn's loopback; `cloudflared` with Testing's tunnel token; `api` and `jobs` on the shared LGTM network;
  - `deploy/testing/compose.env` mapping each service's settings to the `Watt Wise Testing` vault, each service getting only its own ([technical.md](technical.md#cross-cutting)). Claude creates the non-secret items with `op item create`; the developer creates the secrets (database passwords, JWT signing key, tunnel token), the tunnel with its routes for the frontend, admin and API hostnames, and Testing's read-only service account, whose token goes into a root-only file on saturn ([security.md](security.md#deployment));
  - a small wrapper on saturn that runs compose for one environment through `op run` with that environment's token, used for the first start, one-off Cli commands such as `admin grant`, and later by the deploy agent (S5B.9);
  - a new `deploy/docs/environments.md`: the first start (`bootstrap.sql` and the role passwords through `docker compose exec`, as in [postgres.md](../deploy/docs/postgres.md#bootstrap)), everyday commands through the wrapper, and one-off Cli commands; a new `deploy/docs/cloudflare.md` listing each tunnel's routes; `deploy/README.md` and postgres.md updated. Host-specific steps go only into the private runbook.

  Done: the wrapper brings Testing up on saturn with images S5B.4 published; `migrate` exits before `api` and `jobs` start, and when it fails they don't start; over HTTPS the API's `/health` reports healthy and the frontend and admin load; a registration on Testing's frontend delivers its confirmation email to Testing's Mailpit, and the link confirms the account; Testing's logs and traces show in the shared Grafana under `deployment.environment.name` `testing`; `docker inspect` of `api` shows neither the `jobs` nor the `cli` database password; no container publishes a port except Mailpit's web UI on loopback; the token file is readable only by root, and Testing's service account fails to read any other vault; after a restart of saturn the stack comes back on its own, without 1Password; no committed file names saturn's address, network or host setup.

- **S5B.8 Staging and Production stacks.** The same stack for Staging and Production, each with its own reference file in `deploy/<environment>/`, vault, read-only service account, tunnel and subdomains, sending email through Brevo instead of Mailpit ([technical.md](technical.md#cross-cutting)). The developer creates the Brevo account on the free plan, verifies the sending domain with its SPF and DKIM records in Cloudflare DNS, and puts one SMTP key per environment in its vault; Claude creates the non-secret items. environments.md and cloudflare.md cover both. Done: Staging and Production each come up through the S5B.7 wrapper with their own reference file; each API's `/health` is healthy on its own hostname; a registration on Staging delivers the confirmation email through Brevo to a real inbox with SPF and DKIM passing, and its raw headers carry no address of saturn's (if they do, the story stops and a provider setting or another provider is decided before it ships); the three environments share no database, volume, tunnel, service account or secret, and each reference file points only at its own vault; `/scalar` answers on Staging and returns 404 on Production.
- **S5B.9 Pull-based deploys.** The deploy flow in [technical.md](technical.md#hosting-and-operations), as [security.md](security.md#deployment) requires it:
  - a workflow that, after S5B.4 has published and signed a push's images, moves the `testing` tag (push to `dev`) or the `staging` tag (push to `main`) to them and creates a GitHub deployment for that environment; it runs in the matching GitHub environment, limited to its branch, with no secrets;
  - the deploy agent in `deploy/agent/`: a script on a systemd timer on saturn, run as root, that for each environment notices a moved tag, verifies every image with `cosign verify` against the identity the environment accepts, deploys by digest through the S5B.7 wrapper with the compose files from the images' own commit, and reports success or failure to the GitHub deployment with a fine-grained token limited to deployments, kept like the service-account tokens. How it fetches and checks those compose files is decided when the story is planned. One deploy per environment at a time;
  - `deploy/docs/agent.md` with what it checks and how to read its logs; `.github/workflows/README.md` and environments.md updated. Installing it on saturn goes into the private runbook.

  Done: after a merge to `main`, Staging runs that SHA's five images within one timer interval, reports healthy, and the GitHub deployment shows success, while Testing is untouched; a push to `dev` does the same for Testing and leaves Staging untouched; pointing a tag at an unsigned image, at one signed by another workflow, or (for Staging) at one built from `dev` makes the agent refuse it, leave the stack as it was, log why, and mark the deployment failed; a migration that fails leaves the previous `api` and `jobs` running and marks the deployment failed; a timer run with no moved tag changes nothing; no workflow holds a credential for saturn, and nothing in this flow can move the `production` tag.

- **S5B.10 Release swap.** A workflow started by hand from `main`, in the `production` GitHub environment, that swaps the `staging` and `production` tags ([technical.md](technical.md#hosting-and-operations)), so the agent deploys Production first and then Staging. The first swap, with Production still empty, only points `production` at Staging's images. environments.md describes releasing and rolling back; the rule that migrations stay compatible with the previous release is in [architecture.md](../backend/docs/architecture.md#persistence). Done: after a swap Production runs the images Staging ran and Staging the ones Production ran, both healthy and both shown in their GitHub deployments; a second swap restores both; when Production's migrate or health check fails, the agent leaves Production's previous `api` and `jobs` running and doesn't deploy Staging's swap; the workflow can't run from another branch or be triggered by a push; the next push to `main` moves the `staging` tag as usual.

## E6. Observability and hardening

Closes the gaps left open on purpose before real users arrive. Limits: rate limiting on the `/api/v1/auth` endpoints, an upload rate and size limit ready for E7 to apply, security headers and a narrowed CORS policy ([security.md](security.md#transport-and-limits)). The Hangfire dashboard stays off the internet, an internal UI on saturn's loopback address like Grafana. Operations: security events in the logs, a trace per job run, Grafana dashboards, a runbook of queries and email alerts; a daily encrypted `pg_dump` per deployed stack and a restore drill performed once ([technical.md](technical.md#hosting-and-operations)). Runs after E4, whose endpoints, sessions and `Admin` role it protects, and after E5B, whose compose stacks, tunnels, nginx images, shared Grafana LGTM and Brevo account it configures ([security.md](security.md#deployment)).

### Stories

- **S6.1 Rate and size limits.** Rate limiting in the Api with the limits and counters in [security.md](security.md#transport-and-limits): one per-IP counter shared by all `/api/v1/auth` endpoints and a second, tighter one shared by the endpoints that send email, plus a named upload policy (per account) and an upload body-size limit that no endpoint uses yet; E7's upload endpoint applies both. The client address is the connection's own address, except when the request arrives from the tunnel container: then it is taken from the `CF-Connecting-IP` header. The tunnel's address comes from one new 1Password item per environment, read through `deploy/<environment>/compose.env` both by the compose file, which gives `cloudflared` that fixed address on the stack's network, and by the Api's setting, so no address is committed (S5B.7, S5B.8); unset, as in Development, the header is never read. The address is never stored or logged. A rejection is not an `ErrorType`: no handler returns it, so 429 and 413 are responses the framework produces, with the `General.<ReasonPhrase>` code of [error-handling.md](../backend/docs/error-handling.md#the-contract-clients-see), which gets a line for both. The rate-limiting meter is added to the collected meters ([observability.md](../backend/docs/observability.md#shared-setup)), and how the limits are wired goes into [architecture.md](../backend/docs/architecture.md#http-surface). Counters live in the Api's memory, which is enough for one instance. A test endpoint module in Api.IntegrationTests stands in for the upload endpoint, as in S4.7. Done: Api integration tests that control time (a controlled clock, or windows shortened through test settings) prove that after 10 requests from one address spread over two `/api/v1/auth` endpoints the 11th within the minute, to a third, returns 429 ProblemDetails with `Retry-After` and code `General.TooManyRequests` while another address still gets through, and that the counter is free again after the minute; that after 5 email-sending requests from one address spread over register and forgot-password the 6th within the hour returns 429 and sends no email; that the 21st upload within an hour by one account returns 429 while another account's upload passes; that a 5 MB + 1 byte body returns 413 ProblemDetails and a 5 MB one passes; that `CF-Connecting-IP` is used when the request comes from the configured tunnel address and ignored when it comes from anywhere else; that no log event or span attribute of a request contains the client address; and that `/health` and the rest of `/api/v1` are not limited.
- **S6.2 Security headers.** The headers in [security.md](security.md#transport-and-limits) on every response of the Api, the Jobs host and the frontend and admin images, where nginx sets them (S5B.2; the rules join the others in `deploy/docs/images.md`). Decided when the story is planned and recorded in security.md: the `Strict-Transport-Security` value, the looser Content-Security-Policy that the Scalar page needs outside Production and the Hangfire dashboard needs on the Jobs host, and how MUI's injected styles are allowed in the apps without opening scripts to `unsafe-inline`. The apps' policy allows inline scripts only by hash (the theme script from S3.3), the service worker from S3.8 and calls to the API origin of that environment; the API origin in the policy comes from the same `API_BASE_URL` that renders `/config.js` (S5B.2), so one image serves each environment's policy. Done: Api and Jobs integration tests prove that a 200, a 404 and a 500 response each carry all four headers, and that only the Scalar and dashboard paths get the looser policy; a test in each app builds it and fails when any inline script in the built `index.html` has no matching hash in the policy; in Development `/scalar` and `/hangfire` load and work with no Content-Security-Policy violation in the browser console; on Staging both apps load, switch theme, sign in and install as PWAs with no violation in the console, and a page that frames either app is refused.
- **S6.3 CORS hardening.** The S2.7 policy is loose on purpose. Narrow it to what E4's endpoints really use: only the methods and request headers that some `/api/v1` endpoint needs, credentials only on the `/api/v1/auth` endpoints (S4.4), and the preflight cache time reviewed and written down. The allowed origins stay the frontend and admin URLs of each environment from 1Password, and the story checks that each deployed environment's `deploy/<environment>/compose.env` maps exactly those two. The outcome replaces the CORS entry in [architecture.md](../backend/docs/architecture.md#http-surface), and the "E6 narrows it" note in [security.md](security.md#transport-and-limits) goes. Done: an Api integration test reads the mapped `/api/v1` endpoints and fails when the policy allows a method no endpoint uses or misses one an endpoint needs; tests prove that a preflight from an origin outside the list, or asking for a header outside the list, gets no CORS headers; that an endpoint outside `/api/v1/auth` never answers with `Access-Control-Allow-Credentials`; and that no response carries a wildcard origin.
- **S6.4 Hangfire dashboard off the internet.** The dashboard is never reachable from the internet; it becomes an internal UI like Grafana ([security.md](security.md#authorization)). In the Testing, Staging and Production compose files the Jobs container's port is published only on saturn's loopback address, at a port from a new 1Password item per environment; no tunnel route leads to the Jobs host, which `deploy/docs/cloudflare.md` states; and no other container can open the dashboard. Inside a container Hangfire's local-requests-only filter sees Docker's gateway address, not loopback, for a request that came through the published port, so which addresses the dashboard accepts becomes a validated Jobs setting from 1Password, empty meaning loopback only as today. The accepted address is the gateway of the stack's own network, not of the shared LGTM network that `jobs` also joins since S5B.7; which network a published-port request arrives from is checked when the story is planned. That gateway is stable only when the network's subnet is fixed, so the subnet comes from a 1Password item that both the compose file and the Jobs setting read, as in S6.1; the filter that reads it replaces Hangfire's default and is described in [jobs.md](../backend/docs/jobs.md#dashboard). Development keeps opening it directly on the loopback address. `deploy/docs/environments.md` says which item holds each environment's port; how to reach saturn stays in the private runbook. Done: Jobs integration tests prove that the dashboard answers 200 to loopback and to a configured address, and 401 to any other address and to a request with no remote address; that a forwarded-address header doesn't change the answer; and that a malformed setting stops the host at start; on Staging the dashboard opens on saturn's loopback address and on no other address of the server, a request to it from the `api` container and one from a container on the shared LGTM network each get 401, and no route of Staging's tunnel leads to the Jobs host.
- **S6.5 Security event logs.** One structured log event, each with its own stable event name, for: a failed sign-in, an account lockout, a refresh token presented twice, a rate-limit rejection, a password reset or change, `admin grant` and `admin revoke`. Events identify the account by its id only: no email address, IP address, token or password appears in any of them, and a failed sign-in for an unknown email carries no identifier at all. The failed sign-in that locks an account writes both its own event and the lockout event. The list of events and their fields goes into [observability.md](../backend/docs/observability.md). Done: integration tests capture the log events through a registered sink, as the S2.8 tests do, and prove that each case above writes its event exactly once with its name and the account id where one exists; that the fifth failed sign-in writes one failed-sign-in and one lockout event; that a successful sign-in writes none of them; and that across all of them no property or rendered message contains the email, the client address, a token or a password used in the test.
- **S6.6 A trace per job run.** A Hangfire server filter in `WattWise.Jobs` starts one span per job run from a `WattWise.Jobs` activity source, named after the job, with the job id and the recurring job id as tags and status Error when the job throws. The run's database calls become its children, so `ParentlessDatabaseSpanFilter` keeps them, while Hangfire's own polling stays dropped ([observability.md](../backend/docs/observability.md#correlation)). A `WattWise.Jobs` meter counts job runs by job and outcome and records their duration, for S6.9's dashboard. The "Not yet" section of [jobs.md](../backend/docs/jobs.md#not-yet) is replaced by a description of both. Done: Jobs integration tests prove that triggering a job that queries the database records one root span for the run with the query's span as its child, and that the log lines written inside the job carry that trace id; that a throwing job's span has status Error; that a succeeded and a failed run each add one to the counter under their outcome; and that an idle server records no spans.
- **S6.7 Database dumps.** The trigger: the `backup` role exists since S2.3 but nothing uses it, and a file copy of a running data folder is not a consistent backup ([technical.md](technical.md#hosting-and-operations)). The Testing, Staging and Production compose stacks get a service, on the pinned PostgreSQL image ([postgres.md](../deploy/docs/postgres.md#version)), that once a day runs `pg_dump` of `wattwise` as `backup` with the password from that vault's `postgres-backup` item, encrypts the compressed custom-format dump with a key from a new 1Password item, writes it under a timestamped name and then deletes all but the newest 2 ([security.md](security.md#elsewhere)). Both values reach only this service through `deploy/<environment>/compose.env`, like every setting since S5B.7. A dump gets its final name only when both steps succeed, so a failed run never replaces a good dump or counts toward the 2. The folder is readable only by the service's user and root. The encryption tool, and how a run's outcome reaches the shared Grafana LGTM for S6.10's alert (E5B ships no container logs to it), are decided when the story is planned and recorded in postgres.md. The folder's path comes from a new 1Password item per environment. Copying it off the server is outside this repo ([technical.md](technical.md#hosting-and-operations)): the developer sets that up, confirms the dumps arrive in the off-server copy, and keeps its details and retention period in the private runbook. A "Backups" section in postgres.md describes the schedule, the local retention and the key; the command to run a dump by hand goes into `deploy/docs/environments.md` only, with the other deployed-stack commands. Done: a test script run against a throwaway PostgreSQL container proves that three runs leave exactly the 2 newest dumps; that a run with a wrong password leaves the existing dumps untouched, writes no partial file and exits non-zero; that a dump can't be read by `pg_restore --list` as stored and can after decrypting with the key; on Staging a dump from the scheduled run is in the folder the next day and the developer confirms it in the off-server copy, no other user on the server can read it, and `docker inspect` of `api` and `jobs` shows neither the `backup` password nor the encryption key.
- **S6.8 Restore drill.** A backup counts only once a restore from it has worked. [postgres.md](../deploy/docs/postgres.md) gets a "Restore" section with two procedures. The drill, during which nothing is merged to `main` so the deploy agent doesn't restart them: stop `api` and `jobs` on Staging through the S5B.7 wrapper, run a dump by hand (S6.7's command), record the row count of every table, start them again, wait for that dump to reach the off-server copy, take it back from there, decrypt it, restore it as `admin` into a scratch database next to `wattwise`, check it and drop the scratch database. A real restore over `wattwise`: run the bootstrap first, since roles are not in a dump, restore, and run the bootstrap again for the database-level settings; table privileges come from the dump itself, because the bootstrap doesn't grant on existing tables ([postgres.md](../deploy/docs/postgres.md#schemas-and-privileges)). The developer performs the drill on Staging once, with Claude writing the steps and fixing them where the drill shows they are wrong. Done: the restored dump came back from the off-server copy, not from the local folder; in the scratch database every table of `app`, `hangfire` and `migrations` has the row count recorded at dump time and the same owner as in the source; `api` and `jobs` have the same table privileges there as in the source; the scratch database is dropped afterwards; and the section records the date of the drill, how long the restore took and the dump's size.
- **S6.9 Dashboards and query runbook.** Grafana dashboards kept as provisioning files under `deploy/`, loaded by the Development LGTM container and by the shared Grafana LGTM on saturn (S5B.6), where each dashboard has a filter on `deployment.environment.name`. The deploy agent doesn't touch the shared LGTM, so the developer updates it with lgtm.md's commands whenever these files change, and lgtm.md says so; the same holds for S6.10's rules. One dashboard for the Api (request rate, 4xx and 5xx rate, latency percentiles per route, rate-limit rejections from S6.1's meter) and one for jobs and the database (job runs, failures and duration from S6.6's meter, Npgsql connections and command duration). A new `deploy/docs/runbook.md` lists the saved queries: find a request by the `traceId` of a ProblemDetails, errors per service, slowest requests, each security event from S6.5, a job run's trace; "Finding a request" moves there from [lgtm.md](../deploy/docs/lgtm.md). Done: `docker compose … up` on a fresh volume shows both dashboards with no manual import, and after a few requests, a rate-limit rejection and a triggered job every panel shows data; every query in the runbook has been run against Development and returns the event it describes; in the shared Grafana both dashboards show Staging's data when filtered to it and none of Testing's.
- **S6.10 Alerts.** Three alert rules as provisioning files next to S6.9's dashboards: the Api's 5xx rate above a threshold, the Api or the Jobs host unhealthy or silent (both have `/health` since S5B.1), and no successful database dump (S6.7) in the last 26 hours. Grafana can't probe hosts that listen on a developer's loopback address, so how each host's health reaches the receiver (for example a metric the hosts export over OTLP, alerting on its value and on no data) is decided when the story is planned and recorded in [observability.md](../backend/docs/observability.md). The dump rule is loaded only in the shared Grafana, since Development has no dump service, and every rule there names the environment it fired for. Alerts are emailed to the address in a new 1Password item: through Mailpit in Development, and from the shared Grafana through Brevo with its own SMTP key, kept in the vault S5B.6 chose. The developer supplies that key when starting the LGTM project, which until now held no secret, so "Deployment" in [security.md](security.md#deployment) gets a line for it; whether Grafana's anonymous Admin access ([lgtm.md](../deploy/docs/lgtm.md)) stays acceptable once it can send email is decided when the story is planned and recorded there. They share Brevo's 300 emails a day with account emails ([technical.md](technical.md#cross-cutting)), so the rules group alerts and repeat a firing one no more than every few hours. The thresholds, the grouping and the repeat interval are chosen when the story is planned and written into `deploy/docs/runbook.md`, with what to do for each alert. Done: in Development, stopping the `postgres` container makes the health alert fire for both hosts in one email that arrives in Mailpit, and starting it again resolves it; stopping the Jobs host alone fires it for Jobs only; a test alert from the shared Grafana reaches the real inbox through Brevo and names its environment, and Staging's dump alert fires when its window is temporarily set shorter than the age of the newest dump and resolves with the real window.

## E7. Consumption objects and CSV import

Consumption object CRUD, any number of objects per account. ESO CSV parser targeting exactly what Mano ESO exports, Europe/Vilnius interpreted and stored as UTC; how DST days appear in the export is still open, see [known-issues.md](known-issues.md#eso-csv-format-around-dst-changes-is-unknown). Hourly rows keyed by `(consumption_object_id, hour_utc)` with upsert so repeated uploads merge. The CSV itself is discarded after import. Upload UI with clear validation feedback. The upload endpoint applies the upload rate and size limits built in S6.1.

## E8. Consumption visualization

Rich, filterable chart of consumption at hourly, daily and monthly resolution using MUI X Charts. Period selection and summary statistics. Mobile-first. Its charts follow [layout.md](../frontend/docs/layout.md#charts).

## E9. Grid plan domain

ESO grid plan model with its pricing components. Household parameters (contracted power, phases) if the ESO tariff structure requires them; this epic resolves that open question in `docs/product.md`. Draft/published lifecycle. Grid plan ingestion job from the ESO source writing drafts. As the first external HTTP source, it brings in WireMock.Net to stub that source in the job's integration tests ([testing.md](../backend/docs/testing.md#external-http-stubs)); E10 and E11 reuse it. Admin UI to create, edit, publish and retire grid plans. Public catalog page for grid plans.

## E10. Provider plan domain

Supplier plan model built from typed pricing components: fixed rate, time-of-use 2- and 4-zone, spot margin, monthly fee, hybrid. Compatibility rules with grid plans so only valid pairs are offered. Draft/published lifecycle. Per-provider fetchers or scrapers, source chosen per provider, writing drafts with change detection so re-runs do not duplicate. Admin review, edit and publish UI. Public catalog page for supplier plans.

## E11. Spot price ingestion

Hangfire job fetching Nord Pool LT day-ahead hourly prices, ENTSO-E primary with Nord Pool or Litgrid open data as fallback. Storage as `(hour_utc, price_eur_mwh)`. Backfill covering at least the range users can upload, gap detection and refill. Admin visibility of price coverage.

## E12. Current plans baseline

User selects their current grid plan and current supplier plan from the catalog, or enters custom pricing when their plan is not listed. Stored per consumption object and editable.

## E13. Estimated cost engine

Pure Domain engine that estimates what a plan would have cost over a period from hourly consumption, spot prices and pricing components. It is explicitly an estimate, not actual billing: no generation, net metering or invoice reconciliation in MVP, but the inputs are shaped so those can be added later. Time-of-use zones evaluated in local time with correct 23- and 25-hour DST days. Monthly and yearly aggregation. Golden-case unit tests in `Domain.Tests`.

## E14. Comparison and ranking

Query that runs the engine over all published grid plans, supplier plans and valid grid+supplier combinations for the selected period and cost basis, ranks by estimated cost and computes estimated savings versus the baseline. Results UI with period and basis controls, defaulting to the last year and monthly basis, with the note that spot results are a backtest estimate, not a forecast. Its screen follows [layout.md](../frontend/docs/layout.md#comparison-results) and its states [layout.md](../frontend/docs/layout.md#result-states).

## E15. GDPR: export and delete

Full data export bundle for an account. Full account deletion cascading through consumption objects, consumption rows and baselines. Confirmation flows in the UI.

## Out of scope for MVP

Prosumer support, multiple consumption objects in the UI, OAuth sign-in and price alerts are non-goals per `docs/product.md` and have no epics.
