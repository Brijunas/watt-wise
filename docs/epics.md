# Watt-Wise — MVP Epics

Epics are ordered by dependency. Each one is expected to be delivered end to end (backend, frontend, tests) before the next starts, except where noted. `docs/product.md`, `docs/technical.md` and each project's own docs (e.g. `backend/docs/`) remain the source of truth; an epic never overrides them. When an epic's last story ships, the epic moves to [implemented.md](implemented.md).

## E3. Frontend foundation (frontend + admin + shared packages)

Creates the `frontend/` and `admin/` Vite React TypeScript apps in the workspace. Both PWAs booting with the app shell cached. MUI CSS-variables theme with light/dark/auto, choice in `localStorage` and applied before first paint. React Router shell, RTK Query store. Packages `@wattwise/ui`, `@wattwise/core`, `@wattwise/i18n` (LT/EN) and `@wattwise/api-client` with the `@rtk-query/codegen-openapi` pipeline from the API's OpenAPI document. Vitest + React Testing Library set up in every app and package. Extends `docs/development.md` with the app commands. Runs after E2 because the API client is generated from the real OpenAPI document.

### Stories

- **S3.1 Create the two Vite apps.** The developer runs `pnpm create vite` for `frontend/` and `admin/` with the React TypeScript template so the template matches the current release. Claude then:
  - adds them to the workspace, extends `tsconfig.base.json` and the shared ESLint/Prettier/Vitest configs, links the four `@wattwise/*` packages with `workspace:*` and adds one smoke component test each;
  - puts versions both apps share (React, MUI, Redux, i18next) in a pnpm catalog in `pnpm-workspace.yaml`, referenced as `catalog:`. Whenever an E3 story makes a package import a framework library (React, MUI, i18next, Redux), it adds that library to the package's `peerDependencies` and `devDependencies`; the apps own the real versions;
  - moves the template's files into the layout of [frontend-structure.md](frontend-structure.md#layout) (`src/main.tsx`, `src/app/app.tsx`) with the `@/` alias for `src/`. Other folders appear when their first file does;
  - adds the import rules from [frontend-structure.md](frontend-structure.md#enforcement) to the root `eslint.config.js` with `eslint-plugin-import-x`, scoped to each app: a TypeScript import resolver that reads the tsconfig `paths`, the `no-restricted-paths` zones with their `testing/` exception, the per-feature zones generated from each app's `src/features/` listing (no folder yet means no feature zones), the zones for the package graph, `no-cycle`, and `no-restricted-imports` for `useSelector` and `useDispatch` from `react-redux`, off for `stores/hooks.ts`.

  Done: `pnpm --filter frontend dev/build/test` and the same for admin work. In either app, temporarily adding each of these makes `pnpm lint` fail, and removing it makes it pass again: an `@/features/a/…` import in `features/b` (with both folders created for the check), an `@/features/…` or `@/app/…` import in a shared folder, an `@/app/…` import in a feature, an `@wattwise/api-client` import in `@wattwise/ui`, an import cycle, and an import of `useSelector` from `react-redux` in a file other than `stores/hooks.ts`. The exceptions lint clean, with the files created for the check where they don't exist yet: `testing/` importing `@/app/provider` and `stores/hooks.ts` importing `useSelector`.

- **S3.2 Pre-commit hook covers the apps.** Confirm the S1.2 hook (Husky + root `lint-staged.config.js`) lints and formats staged files in `frontend/` and `admin/`. Adjust the lint-staged globs or ESLint config only if app files are missed. Done: a commit with a lint error in either app is rejected locally.
- **S3.3 MUI theme with light/dark/auto.** `@wattwise/ui` exports the MUI CSS-variables theme with `colorSchemes`, a `ThemeProvider` wrapper and a mode switch using `useColorScheme`. The choice is stored in `localStorage` and an inline `<head>` script applies it before first paint. Both apps use it. Done: no flash on reload in either mode, mode switch covered by RTL tests.
- **S3.4 App shell and routing.** React Router in both apps with a mobile-first layout from `@wattwise/ui`: app bar, bottom navigation on phone and side navigation from the `md` breakpoint up, placeholder routes and a not-found page. Done: shell renders correctly at `xs` and `md` in component tests.
- **S3.5 i18n.** `@wattwise/i18n` sets up react-i18next with LT and EN resources, browser-language detection, a language switch component and a typed key convention. Both apps wrap with it. Done: switching language re-renders the shell, tests cover detection and switching.
- **S3.6 RTK Query store and generated API client.** `@wattwise/api-client` gets the `@rtk-query/codegen-openapi` config pointing at the API's OpenAPI document from S2.7, a `pnpm generate:api` root script and the committed output. No sample endpoint exists (S2.5 dropped it); which endpoint S3.6 uses is decided when S3.6 is planned. `@wattwise/core` provides the base query and the Redux store factory, which takes the API slice, the API base URL and a `devTools` flag as parameters; each app reads the URL in its `config/env.ts` and passes `import.meta.env.DEV` as the flag ([frontend-structure.md](frontend-structure.md#store)). The package's entry point exports the enhanced API (cache tags, [frontend-structure.md](frontend-structure.md#where-things-go)) and its hooks; nothing imports the generated file directly. Both apps mount the store and call that endpoint from a page whose feature folder follows [frontend-structure.md](frontend-structure.md#features). Done: regenerating produces no diff, the call renders data in both apps.
- **S3.7 Forms foundation.** react-hook-form with zod resolver, shared zod helpers in `@wattwise/core`, MUI-bound form fields in `@wattwise/ui` with error display and localized messages. One demo form under test. Done: validation errors show localized messages.
- **S3.8 PWA.** `vite-plugin-pwa` in both apps with manifest, icons, app-shell precaching and a network-only rule for `/api`. Update prompt when a new service worker is available. Done: Lighthouse reports installable, API requests are never served from cache.
- **S3.9 Vite env and config.** `.env.example` per app and env files for development/testing/staging/production with the API base URL, typed via `import.meta.env` declarations. E5 releases to Production by moving the images Staging runs there unchanged ([technical.md](technical.md#hosting-and-operations)), so a deployed frontend or admin image must reach the API of whichever environment runs it: either the URL is read when the container starts, or each environment gets its own image. Which one is investigated and decided when S3.9 is planned, recorded in technical.md, and this Done adjusted to it. Done: builds for each mode pick the correct API URL.
- **S3.10 App commands in development.md.** Extend `docs/development.md` with app dev/build/test, single test and API client regeneration commands. Done: each command executed and works.

## E4. Accounts and authentication

ASP.NET Core Identity with email and password: an account signs in only after confirming its email, and a forgotten password is reset through an emailed link. JWT access token plus a rotating refresh token in an httpOnly cookie; each sign-in is a session the user can see and end, one device at a time or everywhere at once ([security.md](security.md)). Transactional email over SMTP: Mailpit in Development and Testing, Brevo in Staging and Production ([technical.md](technical.md#cross-cutting)). `Admin` role guarding `/api/v1/admin`, granted with a `WattWise.Cli` command. Sign-up, sign-in, password and device pages with protected routes in the frontend; sign-in in the admin app. The account model leaves room for OAuth logins later without exposing them. Rate limiting on the auth endpoints and admin access to the Hangfire dashboard stay in E6. The backend stories (S4.1–S4.7) build on E2 and can start now; the app stories (S4.8–S4.10) need E3's routing, forms, i18n and generated API client.

### Stories

- **S4.1 Identity and the account model.** ASP.NET Core Identity in `WattWise.Infrastructure` on `AppDbContext`, its tables in the `app` schema, with the account rules in [security.md](security.md#accounts): email as the unique sign-in name, compared without regard to case; a confirmed email required to sign in; the password rules; the lockout. Each account also keeps a preferred language (LT or EN) for its emails. Identity's external-login table stays in the model so OAuth can be added later, but nothing uses it. The Data Protection keys behind email links are stored in the database. One migration, applied by `WattWise.Cli migrate`. The `api` role already reads and writes every `app` table ([postgres.md](../deploy/docs/postgres.md#roles)), so no grant changes. Done: `WattWise.Cli migrate` applies the migration to a fresh and to an already-migrated database; Infrastructure integration tests prove that a password shorter than 14 characters or missing any required character class is rejected, that a second account whose email differs only in case is rejected, that the fifth failed sign-in in a row locks the account for 15 minutes, and that an email token issued before a host restart is still valid after it; `dotnet ef migrations has-pending-model-changes` passes.
- **S4.2 Email sending.** An Application port for sending email, implemented in Infrastructure over SMTP with MailKit. Its settings are a validated `Smtp` section filled from 1Password through the Api's `.env.<environment>` file; the host stops at start when one is missing, like `Database`. Messages come from LT and EN templates (plain text and HTML), picked by the account's preferred language. The Development compose stack gets a Mailpit container whose SMTP and web addresses come from new 1Password items; `deploy/docs/`, `docs/setup.md` and `docs/development.md` say how to start it and where to read the caught emails. Mailpit for Testing and the Brevo account for Staging and Production are set up in E5. Done: an Infrastructure integration test sends a message through the port to a Mailpit Testcontainer and reads it back through Mailpit's API with the right recipient, subject and language; the Api stops at start when an `Smtp` setting is missing; an email sent by the Development Api shows up in Mailpit's web UI.
- **S4.3 Registration and email confirmation.** Register (email, password, language), confirm-email and resend-confirmation endpoints under `/api/v1/auth`. Registering creates an unconfirmed account and emails a link to the frontend's confirmation page. Neither registering nor resending reveals whether an email already has an account: both give the same response either way, and the owner of an existing account gets an email saying someone tried to register with it instead of a link. Done: Api integration tests, reading the emails from a test double, prove that following the link confirms the account; that a second use of the link, an altered link and another account's link all fail; that registering a taken email returns the same status and body as a new one and creates no second account; that a password breaking the rules returns 400 ProblemDetails with field errors; and that the email comes in the language sent at registration.
- **S4.4 Sign-in, refresh and sign-out.** Sign-in, refresh and sign-out endpoints under `/api/v1/auth`, following the flow in [technical.md](technical.md#backend) and the token rules in [security.md](security.md#tokens), plus `GET /api/v1/me` with the signed-in account's email, language and roles. JWT bearer authentication on the `/api/v1` group, with the signing key from 1Password through the Api's `.env.<environment>` file; the auth endpoints get a CORS policy that allows credentials, the rest of `/api/v1` keeps the S2.7 policy. Each sign-in starts a session that records what [security.md](security.md#sessions) lists (device label, sign-in time, last use), and sign-out ends it. Wrong credentials, an unconfirmed email and a locked-out account each have their own error code, and the unconfirmed code is returned only after the password is checked. Done: Api integration tests prove that `/me` answers with a valid access token and returns 401 ProblemDetails with none, an expired one or a tampered one; that refresh returns a new access token and cookie, and replaying the old cookie fails and ends the session, so the new cookie fails too; that after sign-out the cookie no longer refreshes; that the cookie is httpOnly, Secure, `SameSite=Strict` and limited to the auth path; that with a controlled clock the access token expires after 15 minutes and the refresh token after 7 days; and that a preflight to an auth endpoint allows credentials for the configured origins and no others.
- **S4.5 Password reset and change.** Forgot-password (emails a reset link to the frontend's reset page), reset-password (sets a new password from a valid link) and change-password for a signed-in account (needs the current password), under `/api/v1/auth`. Forgot-password gives the same response whether or not the email has an account. A reset or a change ends every session of the account. Done: Api integration tests prove that a reset link sets the new password and the old one stops working; that a link fails on its second use and after 1 hour; that an unknown email gets the same response and no email is sent; that the new password must follow the rules; that every refresh token issued before a reset or a change is rejected afterwards; and that a change with the wrong current password fails and leaves the password as it was.
- **S4.6 Sessions and devices.** Endpoints under `/api/v1/auth` for the signed-in account to list its sessions (device label, sign-in time, last use, the current one marked), end one of them, and sign out everywhere, which ends every session including the current one ([security.md](security.md#sessions)). Ending a session stops its refresh token at once; access tokens already issued run out within 15 minutes, as security.md records. Done: Api integration tests prove that two sign-ins show as two sessions with their labels and times and only the caller's marked current; that ending the other session makes its refresh fail while the current one keeps working; that ending the current session works like sign-out; that signing out everywhere makes every session's refresh fail, the current one included, and clears the cookie; that ending another account's session returns the same 404 ProblemDetails as an unknown id and leaves it working; and that a session ended by refresh-token reuse is no longer listed.
- **S4.7 Admin role.** The `Admin` role and an `/api/v1/admin` route group that requires it. The `Forbidden` error category (403) added to `ErrorTypeMapping` and [error-handling.md](../backend/docs/error-handling.md#error-categories). `WattWise.Cli admin grant <email>` and `admin revoke <email>` give the role to an existing confirmed account and take it away; revoking also ends every session of the account, so the role is gone within one access-token lifetime ([security.md](security.md#authorization)). The commands go into `docs/development.md`. No real admin endpoint exists yet, so a test endpoint module in Api.IntegrationTests stands in, as in S2.6. Done: Api integration tests prove that the test admin endpoint returns 401 ProblemDetails to an anonymous call, 403 ProblemDetails to a signed-in non-admin and 200 to an admin; integration tests of the grant and revoke use cases prove that an unknown or unconfirmed email fails and changes nothing, and that after a revoke the account's sessions no longer refresh; `admin grant` run against the Development database lets that account call the admin group.
- **S4.8 Token handling in the clients.** `@wattwise/core` gets the session state: the access token kept in memory only, a refresh when the app starts so the cookie restores the session after a reload, and a base query that on a 401 refreshes once and retries, with requests failing together sharing one refresh; a failed refresh signs out. Requests to the auth endpoints send credentials. `@wattwise/api-client` regenerated with E4's endpoints. Done: Vitest tests prove that a start with a valid cookie restores the session without showing sign-in; that two requests failing with 401 at once cause one refresh and are both retried; that a failed refresh clears the session; and that no token is ever written to `localStorage` or `sessionStorage`; `pnpm generate:api` produces no diff.
- **S4.9 Frontend account pages.** In `frontend/`: sign-up, "check your email", the confirmation page the email links to, sign-in, forgot password, reset password, change password, a devices page (the sessions from S4.6, ending one, signing out everywhere) and sign-out, built on S3.7's forms in LT and EN; sign-up sends the current UI language. Each error code from S4.3–S4.6 shows a localized message: an unconfirmed email offers to resend the link, a locked-out account says when to try again. Protected routes send a signed-out user to sign-in and back to the page they asked for afterwards. Done: RTL tests cover each page's success and error states; ending the current session or signing out everywhere on the devices page sends the user to sign-in; a protected route redirects to sign-in and returns to the requested page after it; every page renders at `xs` and `md` in both languages.
- **S4.10 Admin app sign-in.** `admin/` gets sign-in and sign-out on `@wattwise/core`, and every route requires an account with the `Admin` role (from `/me`). A signed-in account without it sees a no-access page and is signed out. The admin app has no sign-up or reset pages; its forgot-password link opens the frontend's page. Done: RTL tests prove that an anonymous visit shows sign-in, a non-admin sees the no-access page and ends signed out, an admin reaches the shell, and an admin's session survives a reload.

## E5. Deployment and CI/CD

Ships Watt-Wise to saturn. Docker images for api, jobs, cli, frontend and admin, built and signed by GitHub Actions. Testing, Staging and Production as Compose stacks on saturn, each with its own PostgreSQL, 1Password vault, Cloudflare Tunnel and subdomains, and one shared Grafana LGTM for their logs, traces and metrics. Deploys are pulled: GitHub Actions moves a registry tag (`dev` → Testing, `main` → Staging, a manual swap of Staging and Production), and an agent on saturn verifies the signatures and deploys. Nothing connects into saturn, and the repo says nothing about it beyond its name. The flow is under "Hosting and operations" in [technical.md](technical.md#hosting-and-operations), the rules under "Deployment" and "CI and contributions" in [security.md](security.md#deployment). Renovate opens the dependency update PRs. It comes after E4 because the stacks need E4's SMTP and JWT settings, and after E3 because the frontend and admin images build its apps; S5.1, S5.3 and S5.6 don't need E3 and can start earlier. From here on every merge to `main` ships to Staging.

### Stories

- **S5.1 Backend images.** Dockerfiles for `WattWise.Api`, `WattWise.Jobs` and `WattWise.Cli`, built from the repo root with a `.dockerignore`: the SDK only in the build stage, a runtime image without it, a non-root user. The images hold no settings or secrets: no `.env*` file and no `appsettings.*.local.json`; everything arrives as environment variables ([technical.md](technical.md#cross-cutting)). The Cli image's entry point is the Cli, so `docker run <image> migrate` migrates. The Jobs host gets the same `/health` with a database check as the Api ([jobs.md](../backend/docs/jobs.md) records it), and both images get a container health check on it. How the images are built and run goes into a new `deploy/docs/images.md`, the build commands into `docs/development.md`. Done: each image builds from the repo root; `docker image inspect` shows a non-root user; the runtime images contain no .NET SDK and no `.env*` file; the Cli image migrates the Development database, and the Api and Jobs images then start against it and report healthy, with their settings passed by `op run` from the existing `.env.development` files; a Jobs integration test covers its `/health` like the Api's.
- **S5.2 Frontend and admin images.** One image each for `frontend/` and `admin/`: the Vite build in a Node stage, served by `nginxinc/nginx-unprivileged` as a non-root user ([technical.md](technical.md#hosting-and-operations)). A path that isn't a file falls back to `index.html` for the router, except under the hashed assets folder, where a missing file is a 404. Hashed assets are cached for a year as immutable; `index.html`, the service worker and the manifest are never cached, so a release reaches users on their next visit through S3.8's update prompt. How the image reaches its environment's API follows S3.9's decision, and the image must run unchanged in Staging and then Production. The nginx rules go into `deploy/docs/images.md`. Done: each image builds from the repo root; against a running container, a deep link to a client route returns `index.html` with 200, a missing hashed asset returns 404, a hashed asset carries `Cache-Control: public, max-age=31536000, immutable`, and `index.html` and the service worker carry `no-cache`; the container runs as a non-root user; an image built once reaches Staging's API when run with Staging's settings and Production's with Production's (or, if S3.9 chose one image per environment, each variant reaches its own).
- **S5.3 Pull request workflow.** A workflow in `.github/workflows/` on every pull request to `main`: the tools from `mise.toml`, the checks in [development.md](development.md#checks), `dotnet ef migrations has-pending-model-changes`, a Betterleaks scan of the PR's commits (the local hook can be skipped, CI can't), zizmor over the workflows, and a build of every image that exists (S5.1, S5.2) without pushing. It follows "CI and contributions" in [security.md](security.md#ci-and-contributions): `pull_request`, never `pull_request_target`; no secrets; each job's `permissions` set explicitly; every action pinned to a full commit SHA. The developer enables GitHub Actions and, in the repository settings, requires SHA-pinned actions, stops Actions from creating or approving pull requests, keeps fork workflows waiting for approval for all external contributors, and adds the check to `main`'s ruleset, which already requires signed commits and pull requests. `.github/workflows/README.md` and development.md say what CI runs. Done: throwaway PRs each fail the check and can't be merged when they add an ESLint error, an unformatted file, a type error, a failing JS or .NET test, a backend build warning, a model change without a migration, a fake secret in a commit, a Dockerfile that no longer builds, an action referenced by tag instead of SHA, or a workflow zizmor flags; a clean PR passes and squash-merges as a commit GitHub shows as verified; a new push to a PR cancels its run still in progress.
- **S5.4 Image publishing and signing.** A workflow that, on every push to `main` and `dev`, builds the five images, pushes them to GitHub Container Registry tagged with the commit SHA, with the OCI labels for the source repository and revision, and signs each by digest with keyless cosign ([security.md](security.md#deployment)). Only the signing job gets `id-token: write`, and only the push job package write. The packages are public like the repository, since the images hold nothing secret (S5.1). How to verify an image by hand goes into `deploy/docs/images.md`. Done: after a push to `dev`, the five images for that SHA are in GHCR, pull without credentials and carry that SHA as their revision label; `cosign verify` with this workflow's identity on `refs/heads/dev` accepts them, and with the identity on `refs/heads/main` rejects them; the same holds the other way round for a push to `main`; an image pushed by hand or from any other workflow fails both; a pull request never pushes or signs an image; a second push of the same SHA leaves the published images as they were.
- **S5.5 Renovate.** The developer installs the Mend-hosted Renovate app on the repo; Claude adds `renovate.json` with the policy in [technical.md](technical.md#repository): npm through pnpm, NuGet through `backend/Directory.Packages.props`, the Docker images in the Dockerfiles and compose files, GitHub Actions and `mise.toml`; a one-day minimum release age; related packages grouped (e.g. React, MUI, typescript-eslint, OpenTelemetry, EF Core with Npgsql); majors in their own PRs; actions pinned to commit SHAs with the version as a comment (`helpers:pinGitHubActionDigests`). It follows [known-issues.md](known-issues.md) and [postgres.md](../deploy/docs/postgres.md#version): the `typescript` alias stays on 6, the .NET SDK pin in `mise.toml` and `global.json` moves together, and PostgreSQL never gets a major bump, while its tag in the compose files and in `PostgresContainerFixture` changes in one PR. "Updating dependencies" in development.md says how Renovate's PRs are handled. Done: `renovate-config-validator` accepts `renovate.json`; Renovate's dependency dashboard lists dependencies from every manager above; its first PRs run the S5.3 check, and its action updates keep SHA pins; no PR proposes the `typescript` alias at 7, a PostgreSQL major, or a release younger than a day.
- **S5.6 Shared Grafana LGTM on saturn.** A Compose project on saturn running `grafana/otel-lgtm`, the image Development uses ([lgtm.md](../deploy/docs/lgtm.md)). The three stacks reach its OTLP receiver over a shared Docker network; the receiver publishes no port. Grafana publishes only on saturn's loopback, at a port from a new 1Password item (which vault holds it is decided when the story is planned), with the same anonymous access as in Development ([security.md](security.md#deployment)). Its data lives in a volume. The developer starts and updates it on saturn; lgtm.md gets a section with those commands, and how to reach saturn goes only into the private runbook. Done: the project comes up healthy with `up -d --wait`; Grafana answers on saturn's loopback and on no other address; the OTLP port is reachable from a container on the shared network and not from saturn's host network or the internet; the data survives `docker compose down` and `up`.
- **S5.7 Testing stack.** Testing runs on saturn from `deploy/`:
  - a Compose file for Testing with PostgreSQL 18.6 (the Development hardening flags, no published port); a one-shot `cli` service running `migrate` that `api` and `jobs` wait for (`depends_on: condition: service_completed_successfully`); `api`, `jobs`, `frontend` and `admin` by image digest; Mailpit with its web UI on saturn's loopback; `cloudflared` with Testing's tunnel token; `api` and `jobs` on the shared LGTM network;
  - `deploy/testing/compose.env` mapping each service's settings to the `Watt Wise Testing` vault, each service getting only its own ([technical.md](technical.md#cross-cutting)). Claude creates the non-secret items with `op item create`; the developer creates the secrets (database passwords, JWT signing key, tunnel token), the tunnel with its routes for the frontend, admin and API hostnames, and Testing's read-only service account, whose token goes into a root-only file on saturn ([security.md](security.md#deployment));
  - a small wrapper on saturn that runs compose for one environment through `op run` with that environment's token, used for the first start, one-off Cli commands such as `admin grant`, and later by the deploy agent (S5.9);
  - a new `deploy/docs/environments.md`: the first start (`bootstrap.sql` and the role passwords through `docker compose exec`, as in [postgres.md](../deploy/docs/postgres.md#bootstrap)), everyday commands through the wrapper, and one-off Cli commands; a new `deploy/docs/cloudflare.md` listing each tunnel's routes; `deploy/README.md` and postgres.md updated. Host-specific steps go only into the private runbook.

  Done: the wrapper brings Testing up on saturn with images S5.4 published; `migrate` exits before `api` and `jobs` start, and when it fails they don't start; over HTTPS the API's `/health` reports healthy and the frontend and admin load; a registration on Testing's frontend delivers its confirmation email to Testing's Mailpit, and the link confirms the account; Testing's logs and traces show in the shared Grafana under `deployment.environment.name` `testing`; `docker inspect` of `api` shows neither the `jobs` nor the `cli` database password; no container publishes a port except Mailpit's web UI on loopback; the token file is readable only by root, and Testing's service account fails to read any other vault; after a restart of saturn the stack comes back on its own, without 1Password; no committed file names saturn's address, network or host setup.

- **S5.8 Staging and Production stacks.** The same stack for Staging and Production, each with its own reference file in `deploy/<environment>/`, vault, read-only service account, tunnel and subdomains, sending email through Brevo instead of Mailpit ([technical.md](technical.md#cross-cutting)). The developer creates the Brevo account on the free plan, verifies the sending domain with its SPF and DKIM records in Cloudflare DNS, and puts one SMTP key per environment in its vault; Claude creates the non-secret items. environments.md and cloudflare.md cover both. Done: Staging and Production each come up through the S5.7 wrapper with their own reference file; each API's `/health` is healthy on its own hostname; a registration on Staging delivers the confirmation email through Brevo to a real inbox with SPF and DKIM passing, and its raw headers carry no address of saturn's (if they do, the story stops and a provider setting or another provider is decided before it ships); the three environments share no database, volume, tunnel, service account or secret, and each reference file points only at its own vault; `/scalar` answers on Staging and returns 404 on Production.
- **S5.9 Pull-based deploys.** The deploy flow in [technical.md](technical.md#hosting-and-operations), as [security.md](security.md#deployment) requires it:
  - a workflow that, after S5.4 has published and signed a push's images, moves the `testing` tag (push to `dev`) or the `staging` tag (push to `main`) to them and creates a GitHub deployment for that environment; it runs in the matching GitHub environment, limited to its branch, with no secrets;
  - the deploy agent in `deploy/agent/`: a script on a systemd timer on saturn, run as root, that for each environment notices a moved tag, verifies every image with `cosign verify` against the identity the environment accepts, deploys by digest through the S5.7 wrapper with the compose files from the images' own commit, and reports success or failure to the GitHub deployment with a fine-grained token limited to deployments, kept like the service-account tokens. How it fetches and checks those compose files is decided when the story is planned. One deploy per environment at a time;
  - `deploy/docs/agent.md` with what it checks and how to read its logs; `.github/workflows/README.md` and environments.md updated. Installing it on saturn goes into the private runbook.

  Done: after a merge to `main`, Staging runs that SHA's five images within one timer interval, reports healthy, and the GitHub deployment shows success, while Testing is untouched; a push to `dev` does the same for Testing and leaves Staging untouched; pointing a tag at an unsigned image, at one signed by another workflow, or (for Staging) at one built from `dev` makes the agent refuse it, leave the stack as it was, log why, and mark the deployment failed; a migration that fails leaves the previous `api` and `jobs` running and marks the deployment failed; a timer run with no moved tag changes nothing; no workflow holds a credential for saturn, and nothing in this flow can move the `production` tag.

- **S5.10 Release swap.** A workflow started by hand from `main`, in the `production` GitHub environment, that swaps the `staging` and `production` tags ([technical.md](technical.md#hosting-and-operations)), so the agent deploys Production first and then Staging. The first swap, with Production still empty, only points `production` at Staging's images. environments.md describes releasing and rolling back; the rule that migrations stay compatible with the previous release is in [architecture.md](../backend/docs/architecture.md#persistence). Done: after a swap Production runs the images Staging ran and Staging the ones Production ran, both healthy and both shown in their GitHub deployments; a second swap restores both; when Production's migrate or health check fails, the agent leaves Production's previous `api` and `jobs` running and doesn't deploy Staging's swap; the workflow can't run from another branch or be triggered by a push; the next push to `main` moves the `staging` tag as usual.

## E6. Observability and hardening

Log queries and traces for Serilog + OpenTelemetry. Hangfire dashboard access control, and its tunnel route once it has it. Rate limiting on auth and upload endpoints, upload size limits, security headers. CORS hardening before the MVP release: the S2.7 policy is deliberately loose, so narrow it to the exact production origins per environment, the methods and headers the endpoints really use, credentials only where E4's refresh cookie needs them, and a reviewed preflight cache. Backup restore drill documented and performed once.

## E7. Consumption objects and CSV import

Consumption object CRUD, any number of objects per account. ESO CSV parser targeting exactly what Mano ESO exports, Europe/Vilnius interpreted and stored as UTC; how DST days appear in the export is still open, see [known-issues.md](known-issues.md#eso-csv-format-around-dst-changes-is-unknown). Hourly rows keyed by `(consumption_object_id, hour_utc)` with upsert so repeated uploads merge. The CSV itself is discarded after import. Upload UI with clear validation feedback.

## E8. Consumption visualization

Rich, filterable chart of consumption at hourly, daily and monthly resolution using MUI X Charts. Period selection and summary statistics. Mobile-first.

## E9. Grid plan domain

ESO grid plan model with its pricing components. Household parameters (contracted power, phases) if the ESO tariff structure requires them; this epic resolves that open question in `docs/product.md`. Draft/published lifecycle. Grid plan ingestion job from the ESO source writing drafts. Admin UI to create, edit, publish and retire grid plans. Public catalog page for grid plans.

## E10. Provider plan domain

Supplier plan model built from typed pricing components: fixed rate, time-of-use 2- and 4-zone, spot margin, monthly fee, hybrid. Compatibility rules with grid plans so only valid pairs are offered. Draft/published lifecycle. Per-provider fetchers or scrapers, source chosen per provider, writing drafts with change detection so re-runs do not duplicate. Admin review, edit and publish UI. Public catalog page for supplier plans.

## E11. Spot price ingestion

Hangfire job fetching Nord Pool LT day-ahead hourly prices, ENTSO-E primary with Nord Pool or Litgrid open data as fallback. Storage as `(hour_utc, price_eur_mwh)`. Backfill covering at least the range users can upload, gap detection and refill. Admin visibility of price coverage.

## E12. Current plans baseline

User selects their current grid plan and current supplier plan from the catalog, or enters custom pricing when their plan is not listed. Stored per consumption object and editable.

## E13. Estimated cost engine

Pure Domain engine that estimates what a plan would have cost over a period from hourly consumption, spot prices and pricing components. It is explicitly an estimate, not actual billing: no generation, net metering or invoice reconciliation in MVP, but the inputs are shaped so those can be added later. Time-of-use zones evaluated in local time with correct 23- and 25-hour DST days. Monthly and yearly aggregation. Golden-case unit tests in `Domain.Tests`.

## E14. Comparison and ranking

Query that runs the engine over all published grid plans, supplier plans and valid grid+supplier combinations for the selected period and cost basis, ranks by estimated cost and computes estimated savings versus the baseline. Results UI with period and basis controls, defaulting to the last year and monthly basis, with the note that spot results are a backtest estimate, not a forecast.

## E15. GDPR: export and delete

Full data export bundle for an account. Full account deletion cascading through consumption objects, consumption rows and baselines. Confirmation flows in the UI.

## Out of scope for MVP

Prosumer support, multiple consumption objects in the UI, OAuth sign-in and price alerts are non-goals per `docs/product.md` and have no epics.
