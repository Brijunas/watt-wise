# Watt-Wise — MVP Epics

Epics are ordered by dependency. Each one is expected to be delivered end to end (backend, frontend, tests) before the next starts, except where noted. `docs/product.md`, `docs/technical.md` and each project's own docs (`backend/docs/`, `frontend/docs/`, `deploy/docs/`) remain the source of truth; an epic never overrides them. When an epic's last story ships, the epic moves to [implemented.md](implemented.md).

## E5C. Testing and the pipeline

Delivers Testing end to end on tethys, proving every part of the deploy flow on a stack with no real data before it reaches Staging and Production. GitHub Actions builds, publishes and signs the images and a deploy bundle; Renovate keeps dependencies current; tethys gets an LGTM for Development and Testing; Testing runs as a second Compose project next to Development and is reached only through SSH forwards, with no tunnel and no public hostname; and a deploy agent on tethys pulls, verifies and deploys, first plainly and then with Caddy blue/green so a deploy has no downtime. The flow is under "Hosting and operations" in [technical.md](technical.md#hosting-and-operations), the rules under "Deployment" and "CI and contributions" in [security.md](security.md#deployment). It depends on E5B for the images, the PR workflow, the first-start services and tethys. E5D reuses everything built here on phoebe. Until a push-to-main workflow exists, a PR's build caches only serve the same PR, so consider a cache-warming workflow on `main`.

### Stories

- **S5C.1 Image publishing and signing.** A long-lived `dev` branch, created by the developer: pushing any branch to it puts that code on Testing, while feature PRs still go to `main`. A workflow that, on every push to `main` and `dev`, builds the four images (Api, Jobs, frontend, admin) and pushes them to GitHub Container Registry tagged with the commit SHA, with the OCI labels for the source repository and revision, and signs each by digest with keyless cosign ([security.md](security.md#deployment)). The same workflow packs `deploy/` (the compose files, `compose.env` files and Caddy config) and a self-contained `WattWise.Cli` binary, which the deploy agent runs to `migrate` (the Cli has no image), as a deploy bundle, an OCI artifact tagged with the SHA and signed the same way, so the VMs never clone the repository. The bundle moves with its environment's tag like the images; which tool packs it is decided when the story is planned. Only the signing job gets `id-token: write`, and only the push job package write. The packages are public like the repository, since they hold nothing secret (S5B.2). How to verify an image or the bundle by hand goes into `deploy/docs/images.md`. Done: after a push to `dev`, the four images and the bundle for that SHA are in GHCR, pull without credentials and the images carry that SHA as their revision label; `cosign verify` with this workflow's identity on `refs/heads/dev` accepts all five, and the bundle's Cli binary starts and prints its commands, and with the identity on `refs/heads/main` rejects them; the same holds the other way round for a push to `main`; the bundle's files equal `deploy/` at that SHA and hold no secret value; an artifact pushed by hand or from any other workflow fails both; a pull request never pushes or signs anything; a second push of the same SHA leaves the published artifacts as they were.
- **S5C.2 Renovate.** The developer installs the Mend-hosted Renovate app on the repo; Claude adds `renovate.json` with the policy in [technical.md](technical.md#repository): npm through pnpm, NuGet through `backend/Directory.Packages.props`, the Docker images in the Dockerfiles and compose files, GitHub Actions and `mise.toml`; a one-day minimum release age; related packages grouped (e.g. React, MUI, typescript-eslint, OpenTelemetry, EF Core with Npgsql); majors in their own PRs; actions pinned to commit SHAs with the version as a comment (`helpers:pinGitHubActionDigests`). It follows [known-issues.md](known-issues.md) and [postgres.md](../deploy/docs/postgres.md#version): the `typescript` alias stays on 6, the .NET SDK pin in `mise.toml` and `global.json` moves together, and PostgreSQL never gets a major bump, while its tag in the compose files and in `PostgresContainerFixture` changes in one PR. "Updating dependencies" in development.md says how Renovate's PRs are handled. Done: `renovate-config-validator` accepts `renovate.json`; Renovate's dependency dashboard lists dependencies from every manager above; its first PRs run the S5B.1 check, and its action updates keep SHA pins; no PR proposes the `typescript` alias at 7, a PostgreSQL major, or a release younger than a day.
- **S5C.3 Grafana LGTM on tethys.** One `grafana/otel-lgtm` ([lgtm.md](../deploy/docs/lgtm.md)) on tethys for the Development stack running there and for Testing, told apart by `deployment.environment.name`; a local machine's Development stack keeps its own. Retention is 7 days, with a size cap on its data volume. Grafana publishes only on tethys's loopback, with the same anonymous access as in Development ([security.md](security.md#deployment)); the OTLP receiver publishes no port and is reached over a Docker network. Whether it is the Development stack's own `lgtm` container that Testing joins or a separate Compose project, and which vault holds the new 1Password items, is decided when the story is planned. lgtm.md gets the commands and the retention. Done: Grafana answers on tethys's loopback and on no other address; the OTLP port is reachable from a container on the network and not from tethys's host network or the LAN; Development's logs, traces and metrics from tethys show under `deployment.environment.name` `development`; the running configuration shows 7 days for each signal and the volume cap; the data survives `docker compose down` and `up`.
- **S5C.4 Testing stack.** Testing runs on tethys from `deploy/`, a Compose project of its own next to Development's:
  - a Compose file with PostgreSQL 18.6 (the Development hardening flags, no published port; the developer runs `deploy/postgres/db-init.sh` once on its empty database), `api`, `jobs`, `frontend` and `admin` by image digest, Mailpit, and Caddy in front of the apps (the blue/green switch of S5C.6 needs it); no `cloudflared`, no tunnel, no public hostname and no HTTPS for Testing; every published port, Caddy's and Mailpit's web UI, binds to tethys's loopback, and `api` and `jobs` join the LGTM network of S5C.3;
  - `deploy/testing/compose.env` mapping each service's settings to the `Watt Wise Testing` vault, each service getting only its own. Claude creates the non-secret items, whose URLs are `http://localhost` with the forwarded ports, with `op item create`; the developer creates the secrets (database passwords, JWT signing key) and Testing's read-only service account, whose token goes into a root-only file on tethys ([security.md](security.md#deployment));
  - a small wrapper on tethys that runs compose for one environment through `op run` with that environment's token, used for one-off Cli commands such as `admin grant` and later by the deploy agent (S5C.5);
  - `deploy/docs/environments.md` gets Testing's section: how to start it, reach it through SSH forwards, and run one-off Cli commands; `deploy/README.md` and postgres.md are updated. Host-specific steps go only into the private runbook.

  Done: the wrapper brings Testing up on tethys with the images S5C.1 published; the agent's `migrate` (the bundle's Cli binary) runs before `api` and `jobs` start, and when it fails they don't start; through SSH forwards the API's `/health` reports healthy and the frontend and admin load at `http://localhost`; a registration on Testing's frontend delivers its confirmation email to Testing's Mailpit, the link confirms the account and the account signs in; Testing's logs and traces show in tethys's Grafana under `deployment.environment.name` `testing`; `docker inspect` of `api` shows neither the `jobs` nor the Cli's database password; every listening port of the stack is on loopback; the token file is readable only by root, and Testing's service account fails to read any other vault; Testing shares no database or volume with Development's stack; after a restart of tethys the stack comes back on its own, without 1Password; no committed file names tethys's address, network or host setup.

- **S5C.5 Verify-and-deploy agent.** The deploy flow in [technical.md](technical.md#hosting-and-operations), as [security.md](security.md#deployment) requires it, built and proven on Testing:
  - a workflow that, after S5C.1 has published and signed a push to `dev`, moves the `testing` tag of the images and the bundle to them and creates a GitHub deployment; it runs in a `testing` GitHub environment limited to `dev`, with no secrets;
  - the agent in `deploy/agent/`: a script on a systemd timer on tethys, run as root, that notices the moved tag, runs `cosign verify` on the four images and the bundle against the identity Testing accepts (`main` or `dev`), unpacks the bundle and deploys the images by digest through the S5C.4 wrapper (the bundle's Cli binary runs `migrate` first, then the stack), and reports success or failure to the GitHub deployment with a fine-grained token limited to deployments, kept like the service-account tokens. One deploy at a time. A deploy of this story may stop the old containers before starting the new ones; S5C.6 removes that;
  - a Healthchecks.io ping per run (free hosted tier, which the developer signs up for); the ping URL is a secret in 1Password;
  - `deploy/docs/agent.md` with what it checks and how to read its logs; `.github/workflows/README.md` and environments.md updated. The developer installs it on tethys by hand until S5C.7; the steps go into the private runbook.

  Done: after a push to `dev`, Testing runs that SHA's four images within one timer interval, reports healthy, and the GitHub deployment shows success; pointing the tag at an unsigned image, at one signed by another workflow, or at a bundle that isn't signed makes the agent refuse it, leave the stack as it was, log why, and mark the deployment failed; a migration that fails leaves the previous `api` and `jobs` running and marks the deployment failed; a timer run with no moved tag changes nothing; Healthchecks.io shows each run and reports the check down when the timer is stopped past its period; no workflow holds a credential for tethys, and no workflow of this story can move a tag other than `testing`.

- **S5C.6 Zero-downtime deploys.** Caddy blue/green in the agent: the new containers start next to the old ones, the agent waits for their health checks, switches Caddy to them and stops the old; when a health check fails it doesn't switch, which is the rollback. `migrate` still runs first, so the previous release's code must keep working on the migrated schema ([architecture.md](../backend/docs/architecture.md#persistence)). How the Jobs host overlaps while both versions run is decided when the story is planned. agent.md and environments.md are updated. Done: while Testing deploys a new SHA, a loop that requests the API's `/health` and the frontend through Caddy every 100 ms sees no failed request; with a new `api` image that fails its health check, Caddy keeps serving the old one, the old containers are still running and the deployment is marked failed; after a successful deploy no old container is left; deploying the previous SHA again switches back.
- **S5C.7 Deploy-VM provisioning.** A committed provisioning script for the deploy-VM role, generic (the dev-VM script of S5B.8 was removed, so this one is the first): Docker, the deploy agent and its systemd timer, SSH hardening and a firewall, with no value specific to a host. The same script sets up tethys's Testing role and, in E5D, phoebe; it leaves SSH key-only from the LAN on both VMs and nothing else inbound ([security.md](security.md#deployment)). environments.md and agent.md point to it in place of the by-hand steps. Done: run on tethys it leaves the agent timer active and Testing still deploying a new push to `dev`; rerunning it changes nothing; the script and the docs contain no address, hostname or network detail.

## E5D. Staging and Production

Delivers the live stacks on phoebe, a VM on saturn that accepts only key-only SSH from the LAN and nothing from the internet: Staging and Production, both public through Cloudflare Tunnels and reached by their users on their own subdomains. It extends E5C's agent to phoebe (Staging from `main`, Production only through a swap), adds the release swap, and closes the operational gaps with encrypted database dumps pushed off the VM, a restore drill, and alerts to the developer's phone that keep working when saturn itself is down. By its end deploys have no downtime, a failed health check rolls back by not switching, and an external check watches Production. It depends on E5C and on E4's SMTP settings; E6 hardens what runs here, so it comes after.

### Stories

- **S5D.1 Grafana LGTM on phoebe.** One `grafana/otel-lgtm` on phoebe for Staging and Production, told apart by `deployment.environment.name`, with 30 days of retention and a size cap on its data volume. Grafana publishes only on phoebe's loopback and the OTLP receiver on a Docker network only, as in S5C.3; lgtm.md gets the section. The developer reaches Grafana and updates this project over SSH forwards, as on tethys. Done: Grafana answers on phoebe's loopback and on no other address; the OTLP port is reachable from a container on the network and not from phoebe's host network or the internet; the running configuration shows 30 days and the volume cap; the data survives `docker compose down` and `up`.
- **S5D.2 Staging and Production stacks.** The Testing stack of S5C.4 (Caddy in front of the apps, the wrapper) for Staging and Production on phoebe, where the owner runs `db-init` once on each new VM and the deploy agent runs the Cli binary's `migrate`, each a Compose project with its own reference file in `deploy/<environment>/`, vault, read-only service account (token in a root-only file), tunnel and subdomains, sending email through Brevo instead of Mailpit ([technical.md](technical.md#cross-cutting)). Both are public: no Cloudflare Access in front. Each stack's `cloudflared` runs its tunnel with only its token and reaches Caddy, which has a fixed address on the stack's network (the 1Password item S6.1 reads) and passes `CF-Connecting-IP` through only for requests from `cloudflared`; the developer creates the tunnels with their routes for the frontend, admin and API hostnames. The developer creates the Brevo account on the free plan, verifies the sending domain with its SPF and DKIM records in Cloudflare DNS, and puts one SMTP key per environment in its vault; Claude creates the non-secret items. phoebe is provisioned with S5C.7's script; its steps go into the private runbook. environments.md covers both stacks, and a new `deploy/docs/cloudflare.md` lists each tunnel's routes (Testing has none); `deploy/README.md` and postgres.md are updated. Done: Staging and Production each come up through the wrapper with their own reference file; each API's `/health` is healthy over HTTPS on its own hostname and both apps load; a registration on Staging delivers the confirmation email through Brevo to a real inbox with SPF and DKIM passing, and its raw headers carry no address of saturn's or phoebe's (if they do, the story stops and a provider setting or another provider is decided before it ships); the three environments share no database, volume, tunnel, service account or secret, and each reference file points only at its own vault; `/scalar` answers on Staging and returns 404 on Production; no port of phoebe is reachable except SSH from the LAN, and the tunnels are the only way in from the internet; after a restart of phoebe both stacks come back on their own, without 1Password.
- **S5D.3 Deploys to Staging.** The agent of S5C.5 and S5C.6 on phoebe, set up with S5C.7's script: a workflow moves the `staging` tag of the images and the bundle after a push to `main` has been published and signed, in a `staging` GitHub environment limited to `main`; the agent accepts only `main`'s signatures for Staging and Production, and Production's tag is moved only by the swap (S5D.4). Its Healthchecks.io ping is a second check; the fine-grained deployments token is kept as on tethys. agent.md, environments.md and the workflows README are updated. Done: after a merge to `main`, Staging runs that SHA's four images within one timer interval without a failed request, reports healthy, and the GitHub deployment shows success, while Testing is untouched; a push to `dev` leaves Staging untouched; pointing the `staging` tag at an image signed from `dev`, an unsigned one or one signed by another workflow makes the agent refuse it, leave Staging as it was, log why, and mark the deployment failed; a migration that fails leaves the previous `api` and `jobs` running; no workflow holds a credential for phoebe, and nothing in this flow can move the `production` tag.
- **S5D.4 Release swap.** A workflow started by hand from `main`, in the `production` GitHub environment, that swaps the `staging` and `production` tags ([technical.md](technical.md#hosting-and-operations)), so the agent deploys Production first and then Staging. The first swap, with Production still empty, only points `production` at Staging's images. environments.md describes releasing and rolling back; the rule that migrations stay compatible with the previous release is in [architecture.md](../backend/docs/architecture.md#persistence). Done: after a swap Production runs the images Staging ran and Staging the ones Production ran, both healthy and both shown in their GitHub deployments; a second swap restores both; when Production's migrate or health check fails, the agent leaves Production's previous `api` and `jobs` running and doesn't deploy Staging's swap; the workflow can't run from another branch or be triggered by a push; the next push to `main` moves the `staging` tag as usual.
- **S5D.5 Database dumps.** The trigger: the `backup` role exists since S2.3 but nothing uses it, and a file copy of a running data folder is not a consistent backup ([technical.md](technical.md#hosting-and-operations)). The Staging and Production stacks (Testing gets none) get a service, on the pinned PostgreSQL image ([postgres.md](../deploy/docs/postgres.md#version)), that once a day runs `pg_dump` of `wattwise` as `backup` with the password from that vault's `postgres-backup` item, encrypts the compressed custom-format dump with a key from a new 1Password item and pushes it off phoebe to Cloudflare R2 with a write-only key ([security.md](security.md#elsewhere)). Retention is a lifecycle rule of the bucket. A dump gets its final name only when the encryption succeeded, and a failed run never replaces a good dump. A successful run pings a Healthchecks.io check, whose ping URL is a secret in 1Password. All values reach only this service through `deploy/<environment>/compose.env`. The developer creates the bucket, its lifecycle rule and the write-only key, and keeps the retention period in the private runbook. The encryption and upload tools, and whether a local copy stays on phoebe, are decided when the story is planned and recorded in postgres.md, whose new "Backups" section describes the schedule and the key; the command to run a dump by hand goes into environments.md. Proxmox backups of the phoebe VM are the developer's own and live only in the private runbook. Done: a test script run against a throwaway PostgreSQL container proves that a run with a wrong password leaves the existing dumps untouched, writes no partial file and exits non-zero, and that a dump can't be read by `pg_restore --list` as stored and can after decrypting with the key; on Staging a dump from the scheduled run is in the R2 bucket the next day (the developer confirms) and Healthchecks.io shows the ping; the write-only key can't list, read or delete objects; no other user on phoebe can read a local copy if one stays; `docker inspect` of `api` and `jobs` shows neither the `backup` password, the encryption key nor the R2 key; Testing runs no dump service.
- **S5D.6 Restore drill.** A backup counts only once a restore from it has worked. [postgres.md](../deploy/docs/postgres.md) gets a "Restore" section with two procedures. The drill, during which nothing is merged to `main` so the agent doesn't restart the stack: stop `api` and `jobs` on Staging through the wrapper, run a dump by hand (S5D.5's command), record the row count of every table, start them again, take the dump from R2 with a read key that the developer holds and that never sits on phoebe, decrypt it, restore it as `admin` into a scratch database next to `wattwise`, check it and drop the scratch database. A real restore over `wattwise`: run the bootstrap first, since roles are not in a dump, restore, and run the bootstrap again for the database-level settings; table privileges come from the dump itself, because the bootstrap doesn't grant on existing tables ([postgres.md](../deploy/docs/postgres.md#schemas-and-privileges)). The developer performs the drill on Staging once, with Claude writing the steps and fixing them where the drill shows they are wrong. Done: the restored dump came back from R2, not from a local folder; in the scratch database every table of `app`, `hangfire` and `migrations` has the row count recorded at dump time and the same owner as in the source; `api` and `jobs` have the same table privileges there as in the source; the scratch database is dropped afterwards; and the section records the date of the drill, how long the restore took and the dump's size.
- **S5D.7 Alert rules.** Grafana alert rules on phoebe, as provisioning files under `deploy/` loaded by the LGTM of S5D.1: the Api's 5xx rate above a threshold, the Api or the Jobs host unhealthy or silent (both have `/health` since S5B.2), a failed deploy, and a disk almost full. They notify the developer's existing ntfy on tethys, reached over the LAN, outbound from phoebe. Grafana can't probe hosts on a loopback address, so how each host's health, the agent's outcome and the disk level reach Grafana is decided when the story is planned and recorded in [observability.md](../backend/docs/observability.md), as is whether Grafana's anonymous Admin access ([lgtm.md](../deploy/docs/lgtm.md)) stays acceptable once it can send notifications. The thresholds, the grouping and the repeat interval are chosen when the story is planned and written, with what to do for each alert, into a new `deploy/docs/alerts.md`; each notification names the environment it fired for. The deploy agent doesn't touch the LGTM, so the developer updates it with lgtm.md's commands whenever these files change, and lgtm.md says so. Done: on Staging, stopping the `api` container makes the unhealthy alert fire, a notification naming Staging reaches the ntfy topic on tethys and the developer's phone, and starting it again resolves it; stopping the Jobs host alone fires it for Jobs only; a deploy refused for a bad signature fires the failed-deploy alert; a test alert for the disk rule reaches the phone; no rule fires in steady state over an hour.
- **S5D.8 External monitoring.** Alerts that don't depend on saturn: anything running on saturn, tethys included, is silent when saturn is down. Heartbeats go to Healthchecks.io (hosted, free tier, open source): the agent's pings (S5C.5, S5D.3) and the dump's (S5D.5); a missing ping notifies a secret ntfy.sh topic, with email as a second channel. A repo-owned Cloudflare Worker on a cron trigger probes Production's frontend, admin and API `/health` every 5 minutes and notifies the same topic and email on a failure. The ntfy.sh topic name, the ping URLs and Production's hostnames are secrets or Worker settings, never in the repo ([security.md](security.md#deployment)). The developer creates the topic, the Healthchecks.io checks and the Worker's deployment; where the Worker's code lives, how its logic is tested in the checks and how it is deployed is decided when the story is planned. environments.md and alerts.md say what each channel covers. Done: with Production's Api stopped, a notification reaches the ntfy.sh topic and the email address within 10 minutes and a recovery notice follows when it starts; each of the three probed URLs alone raises its own notification; stopping the agent timer past its period and skipping a dump each raise a Healthchecks.io notification; the Worker's logic is covered by a test that passes in `pnpm test`; no topic name, ping URL or hostname is in the repo.

## E6. Observability and hardening

Closes the gaps left open on purpose before real users arrive. Limits: rate limiting on the `/api/v1/auth` endpoints, an upload rate and size limit ready for E7 to apply, security headers and a narrowed CORS policy ([security.md](security.md#transport-and-limits)). The Hangfire dashboard stays off the internet, an internal UI on its VM's loopback address like Grafana. Operations: security events in the logs, a trace per job run, Grafana dashboards and a runbook of queries; the database dumps, the restore drill and the alerts are built in E5D ([technical.md](technical.md#hosting-and-operations)). Runs after E4, whose endpoints, sessions and `Admin` role it protects, and after E5D, whose compose stacks, tunnels, nginx images, Grafana LGTM per VM and Brevo account it configures ([security.md](security.md#deployment)).

### Stories

- **S6.1 Rate and size limits.** Rate limiting in the Api with the limits and counters in [security.md](security.md#transport-and-limits): one per-IP counter shared by all `/api/v1/auth` endpoints and a second, tighter one shared by the endpoints that send email, plus a named upload policy (per account) and an upload body-size limit that no endpoint uses yet; E7's upload endpoint applies both. The client address is the connection's own address, except when the request arrives from the stack's Caddy, which passes `CF-Connecting-IP` through only for requests it received from `cloudflared` so a client can't forge it: then it is taken from that header. Only Staging and Production have a tunnel (S5D.2); Testing is reached through SSH forwards and has none. Caddy's address comes from one new 1Password item per tunnelled environment, read through `deploy/<environment>/compose.env` both by the compose file, which gives Caddy that fixed address on the stack's network, and by the Api's setting, so no address is committed (S5D.2); unset, as in Development and Testing, the header is never read. The address is never stored or logged. A rejection is not an `ErrorType`: no handler returns it, so 429 and 413 are responses the framework produces, with the `General.<ReasonPhrase>` code of [error-handling.md](../backend/docs/error-handling.md#the-contract-clients-see), which gets a line for both. The rate-limiting meter is added to the collected meters ([observability.md](../backend/docs/observability.md#shared-setup)), and how the limits are wired goes into [architecture.md](../backend/docs/architecture.md#http-surface). Counters live in the Api's memory, which is enough for one instance. A test endpoint module in Api.IntegrationTests stands in for the upload endpoint, as in S4.7. Done: Api integration tests that control time (a controlled clock, or windows shortened through test settings) prove that after 10 requests from one address spread over two `/api/v1/auth` endpoints the 11th within the minute, to a third, returns 429 ProblemDetails with `Retry-After` and code `General.TooManyRequests` while another address still gets through, and that the counter is free again after the minute; that after 5 email-sending requests from one address spread over register and forgot-password the 6th within the hour returns 429 and sends no email; that the 21st upload within an hour by one account returns 429 while another account's upload passes; that a 5 MB + 1 byte body returns 413 ProblemDetails and a 5 MB one passes; that `CF-Connecting-IP` is used when the request comes from Caddy's configured address and ignored when it comes from anywhere else, and that Caddy's config drops a `CF-Connecting-IP` header on a request that didn't come from `cloudflared`; that no log event or span attribute of a request contains the client address; and that `/health` and the rest of `/api/v1` are not limited.
- **S6.2 Security headers.** The headers in [security.md](security.md#transport-and-limits) on every response of the Api, the Jobs host and the frontend and admin images, where nginx sets them (S5B.3; the rules join the others in `deploy/docs/images.md`). Decided when the story is planned and recorded in security.md: the `Strict-Transport-Security` value, the looser Content-Security-Policy that the Scalar page needs outside Production and the Hangfire dashboard needs on the Jobs host, and how MUI's injected styles are allowed in the apps without opening scripts to `unsafe-inline`. The apps' policy allows inline scripts only by hash (the theme script from S3.3), the service worker from S3.8 and calls to the API origin of that environment; the API origin in the policy comes from the same `API_BASE_URL` that renders `/config.js` (S5B.3), so one image serves each environment's policy. Done: Api and Jobs integration tests prove that a 200, a 404 and a 500 response each carry all four headers, and that only the Scalar and dashboard paths get the looser policy; a test in each app builds it and fails when any inline script in the built `index.html` has no matching hash in the policy; in Development `/scalar` and `/hangfire` load and work with no Content-Security-Policy violation in the browser console; on Staging both apps load, switch theme, sign in and install as PWAs with no violation in the console, and a page that frames either app is refused.
- **S6.3 CORS hardening.** The S2.7 policy is loose on purpose. Narrow it to what E4's endpoints really use: only the methods and request headers that some `/api/v1` endpoint needs, credentials only on the `/api/v1/auth` endpoints (S4.4), and the preflight cache time reviewed and written down. The allowed origins stay the frontend and admin URLs of each environment from 1Password, and the story checks that each deployed environment's `deploy/<environment>/compose.env` maps exactly those two. The outcome replaces the CORS entry in [architecture.md](../backend/docs/architecture.md#http-surface), and the "E6 narrows it" note in [security.md](security.md#transport-and-limits) goes. Done: an Api integration test reads the mapped `/api/v1` endpoints and fails when the policy allows a method no endpoint uses or misses one an endpoint needs; tests prove that a preflight from an origin outside the list, or asking for a header outside the list, gets no CORS headers; that an endpoint outside `/api/v1/auth` never answers with `Access-Control-Allow-Credentials`; and that no response carries a wildcard origin.
- **S6.4 Hangfire dashboard off the internet.** The dashboard is never reachable from the internet; it becomes an internal UI like Grafana ([security.md](security.md#authorization)). In the Testing, Staging and Production compose files the Jobs container's port is published only on the loopback address of the stack's VM (tethys for Testing, phoebe for Staging and Production), at a port from a new 1Password item per environment; no tunnel route leads to the Jobs host, which `deploy/docs/cloudflare.md` states for Staging and Production (Testing has no tunnel); and no other container can open the dashboard. Inside a container Hangfire's local-requests-only filter sees Docker's gateway address, not loopback, for a request that came through the published port, so which addresses the dashboard accepts becomes a validated Jobs setting from 1Password, empty meaning loopback only as today. The accepted address is the gateway of the stack's own network, not of the LGTM network that `jobs` also joins (S5C.4, S5D.2); which network a published-port request arrives from is checked when the story is planned. That gateway is stable only when the network's subnet is fixed, so the subnet comes from a 1Password item that both the compose file and the Jobs setting read, as in S6.1; the filter that reads it replaces Hangfire's default and is described in [jobs.md](../backend/docs/jobs.md#dashboard). Development keeps opening it directly on the loopback address. `deploy/docs/environments.md` says which item holds each environment's port; how to reach the VMs stays in the private runbook. Done: Jobs integration tests prove that the dashboard answers 200 to loopback and to a configured address, and 401 to any other address and to a request with no remote address; that a forwarded-address header doesn't change the answer; and that a malformed setting stops the host at start; on Staging the dashboard opens on phoebe's loopback address and on no other address of the VM, a request to it from the `api` container and one from a container on the LGTM network each get 401, and no route of Staging's tunnel leads to the Jobs host.
- **S6.5 Security event logs.** One structured log event, each with its own stable event name, for: a failed sign-in, an account lockout, a refresh token presented twice, a rate-limit rejection, a password reset or change, `admin grant` and `admin revoke`. Events identify the account by its id only: no email address, IP address, token or password appears in any of them, and a failed sign-in for an unknown email carries no identifier at all. The failed sign-in that locks an account writes both its own event and the lockout event. The list of events and their fields goes into [observability.md](../backend/docs/observability.md). Done: integration tests capture the log events through a registered sink, as the S2.8 tests do, and prove that each case above writes its event exactly once with its name and the account id where one exists; that the fifth failed sign-in writes one failed-sign-in and one lockout event; that a successful sign-in writes none of them; and that across all of them no property or rendered message contains the email, the client address, a token or a password used in the test.
- **S6.6 A trace per job run.** A Hangfire server filter in `WattWise.Jobs` starts one span per job run from a `WattWise.Jobs` activity source, named after the job, with the job id and the recurring job id as tags and status Error when the job throws. The run's database calls become its children, so `ParentlessDatabaseSpanFilter` keeps them, while Hangfire's own polling stays dropped ([observability.md](../backend/docs/observability.md#correlation)). A `WattWise.Jobs` meter counts job runs by job and outcome and records their duration, for S6.9's dashboard. The "Not yet" section of [jobs.md](../backend/docs/jobs.md#not-yet) is replaced by a description of both. Done: Jobs integration tests prove that triggering a job that queries the database records one root span for the run with the query's span as its child, and that the log lines written inside the job carry that trace id; that a throwing job's span has status Error; that a succeeded and a failed run each add one to the counter under their outcome; and that an idle server records no spans.
- **S6.9 Dashboards and query runbook.** Grafana dashboards kept as provisioning files under `deploy/`, loaded by the Development LGTM container, by the LGTM on tethys (S5C.3) and by the one on phoebe (S5D.1), where each dashboard has a filter on `deployment.environment.name`. The deploy agent doesn't touch the LGTMs, so the developer updates them with lgtm.md's commands whenever these files change, and lgtm.md says so, as it does for S5D.7's rules. One dashboard for the Api (request rate, 4xx and 5xx rate, latency percentiles per route, rate-limit rejections from S6.1's meter) and one for jobs and the database (job runs, failures and duration from S6.6's meter, Npgsql connections and command duration). A new `deploy/docs/runbook.md` lists the saved queries: find a request by the `traceId` of a ProblemDetails, errors per service, slowest requests, each security event from S6.5, a job run's trace; "Finding a request" moves there from [lgtm.md](../deploy/docs/lgtm.md). Done: `docker compose … up` on a fresh volume shows both dashboards with no manual import, and after a few requests, a rate-limit rejection and a triggered job every panel shows data; every query in the runbook has been run against Development and returns the event it describes; in phoebe's Grafana both dashboards show Staging's data when filtered to it and none of Production's, and in tethys's they show Testing's.

## E7. Consumption objects and CSV import

Consumption object CRUD, any number of objects per account. ESO CSV parser targeting exactly what Mano ESO exports, Europe/Vilnius interpreted and stored as UTC; how DST days appear in the export is still open, see [known-issues.md](known-issues.md#eso-csv-format-around-dst-changes-is-unknown). Hourly rows keyed by `(consumption_object_id, hour_utc)` with upsert so repeated uploads merge. The CSV itself is discarded after import. Upload UI with clear validation feedback. The upload endpoint applies the upload rate and size limits built in S6.1.

## E8. Consumption visualization

Rich, filterable chart of consumption at hourly, daily and monthly resolution using MUI X Charts. Period selection and summary statistics. Mobile-first. Its charts follow [layout.md](../frontend/docs/layout.md#charts).

## E9. Grid plan domain

ESO grid plan model with its pricing components. Household parameters (contracted power, phases) if the ESO tariff structure requires them; this epic resolves that open question in `docs/product.md`. Draft/published lifecycle. Grid plan ingestion job from the ESO source writing drafts. As the first external HTTP source, it brings in WireMock.Net to stub that source in the job's integration tests ([testing.md](../backend/docs/testing.md#external-http-stubs)); E10 and E11 reuse it. Admin UI to create, edit, publish and retire grid plans. Public catalog page for grid plans.

## E10. Provider plan domain

Supplier plan model built from typed pricing components: fixed rate, time-of-use 2- and 4-zone, spot margin, monthly fee, hybrid. Compatibility rules with grid plans so only valid pairs are offered. Draft/published lifecycle. Per-provider fetchers or scrapers, source chosen per provider, writing drafts with change detection so re-runs do not duplicate. Admin review, edit and publish UI. Public catalog page for supplier plans.

## E11. Spot price ingestion

Hangfire job fetching Nord Pool LT day-ahead hourly prices, ENTSO-E primary with Nord Pool or Litgrid open data as fallback. Storage as `(hour_utc, price_eur_mwh)`. Backfill covering at least the range users can upload, gap detection and refill. Admin visibility of price coverage.

## E12. Current plans baseline

User selects their current grid plan and current supplier plan from the catalog, or enters custom pricing when their plan is not listed. Stored per consumption object and editable.

## E13. Estimated cost engine

Pure Domain engine that estimates what a plan would have cost over a period from hourly consumption, spot prices and pricing components. It is explicitly an estimate, not actual billing: no generation, net metering or invoice reconciliation in MVP, but the inputs are shaped so those can be added later. Time-of-use zones evaluated in local time with correct 23- and 25-hour DST days. Monthly and yearly aggregation. Golden-case unit tests in `Domain.Tests`.

## E14. Comparison and ranking

Query that runs the engine over all published grid plans, supplier plans and valid grid+supplier combinations for the selected period and cost basis, ranks by estimated cost and computes estimated savings versus the baseline. Results UI with period and basis controls, defaulting to the last year and monthly basis, with the note that spot results are a backtest estimate, not a forecast. Its screen follows [layout.md](../frontend/docs/layout.md#comparison-results) and its states [layout.md](../frontend/docs/layout.md#result-states).

## E15. GDPR: export and delete

Full data export bundle for an account. Full account deletion cascading through consumption objects, consumption rows and baselines. Confirmation flows in the UI.

## Out of scope for MVP

Prosumer support, multiple consumption objects in the UI, OAuth sign-in and price alerts are non-goals per `docs/product.md` and have no epics.
