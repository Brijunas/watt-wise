# S4.3 implementation plan: the email outbox

**Temporary.** This is the agreed plan for S4.3 ([epics.md](epics.md)), written for the session that implements it. When S4.3 ships, its facts move into [email.md](../backend/docs/email.md), [jobs.md](../backend/docs/jobs.md), [accounts.md](../backend/docs/features/accounts.md), [security.md](security.md) and [CLAUDE.md](../CLAUDE.md), and this file is deleted in the same change (see the [checklist](#cleanup-checklist)). Where the plan and a doc disagree, the plan wins until then. Words follow the Vocabulary in accounts.md.

## Shape

The Api no longer sends email. A use case writes a row to `app.email_requests` in the same `SaveChanges` as its account change. The Jobs host polls the table every 5 seconds, creates the link and sends. A request never touches SMTP, so its timing can't show whether an address has an account.

## Write side (Api)

The command handler writes the row explicitly through an Application port, `IEmailRequests.Add(...)`. No domain events, no interceptor. The address is normalized with the existing `EmailLookupNormalizer` rules.

| Flow                   | Account change                                  | Row inserted                                                   |
| ---------------------- | ----------------------------------------------- | -------------------------------------------------------------- |
| Register, new email    | create the `Account` and its `AccountIdentity`  | `EmailConfirmation` for the new account (`account_id`)         |
| Register, taken email  | none; still hash the password and drop the hash | `AccountAlreadyExists` for the existing account (`account_id`) |
| Resend confirmation    | none                                            | `EmailConfirmation` keyed by the normalized address (`email`)  |
| Forgot password (S4.5) | none                                            | `PasswordReset` keyed by the normalized address (`email`)      |

- **Same response:** register answers the same status and body for a taken email, and creates no second account.
- **No lookup:** resend and forgot-password never check whether the address has an account. The worker resolves it.
- **S4.3 writes** `EmailConfirmation` and `AccountAlreadyExists`. S4.5 only adds the `PasswordReset` write; the worker already handles it.
- **Endpoints:** `AccountsEndpointModule` in the Api's `Endpoints/` maps `register`, `confirm-email` and `resend-confirmation` under `/api/v1/auth`. Run `pnpm generate:api` and commit the OpenAPI document and client.

## Table `app.email_requests`

| Column            | Type               | Notes                                                                                                                                         |
| ----------------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`              | `uuid`             | `Guid` v7                                                                                                                                     |
| `kind`            | `text`             | `EmailConfirmation`, `AccountAlreadyExists` or `PasswordReset`                                                                                |
| `account_id`      | `uuid` null        | FK to `accounts`, on delete cascade                                                                                                           |
| `email`           | `text` null        | normalized address; `CHECK (num_nonnulls(account_id, email) = 1)`                                                                             |
| `status`          | `text`             | `pending`, `sending`, `sent`, `superseded`, `failed`; a `CHECK` lists them                                                                    |
| `attempt_count`   | `integer`          | default 0                                                                                                                                     |
| `next_attempt_at` | `timestamptz`      | set to now on insert                                                                                                                          |
| `last_attempt_at` | `timestamptz` null |                                                                                                                                               |
| `last_error`      | `text` null        | an exception type name or an SMTP status only (for example `SmtpCommandException 451`), at most 100 characters; never a message or an address |
| `created_at`      | `timestamptz`      |                                                                                                                                               |
| `sent_at`         | `timestamptz` null |                                                                                                                                               |

- **Never stored:** a token or a link. The link is built in memory and the token's SHA-256 hash lives in `email_link_tokens`.
- **Index:** `ix_email_requests_due` on (`status`, `next_attempt_at`) `WHERE status IN ('pending', 'sending')`. Pending rows are the due ones; `sending` rows are the stuck-row scan. The purge reads the small rest of the table without an index.
- **Statuses:** `pending` → `sending` → `sent`. A retry sends a row back to `pending` with a later `next_attempt_at`. `superseded` and `failed` are final, like `sent`.
- **Migration:** ask the user at implementation time whether to regenerate `Initial` or add a migration ([architecture.md](../backend/docs/architecture.md#persistence)). Claude runs the commands.
- **Access:** the `api` role inserts rows and the `jobs` role reads, updates and deletes them. The `jobs` role already reads and writes `app` (S2.12), so no grant should change; verify it against `deploy/` at implementation and in a test.

## The sender's contract

`IEmailSender.SendAsync` now returns `Task<SendResult>` and takes the Message-Id's local part: `SendAsync(EmailMessage, string messageIdLocalPart, CancellationToken)`. `SmtpEmailSender` appends `@<from domain>`. The caller passes `<row id N>.<attempt number>`, so each attempt has a new Message-Id.

- **`SendResult`:** `Outcome` (`Sent`, `Retryable`, `Permanent`) and `Error` (the `last_error` text).
- **Retryable:** `SmtpCommandException` with a 4xx status, and socket, connect, TLS and timeout failures before DATA.
- **Permanent:** `SmtpCommandException` with a 5xx status.
- **Still throws:** cancellation, and bugs (broken template, missing setting, an address that isn't one). The handler catches a bug per row, records `failed` with the exception's type name and logs it at Error; cancellation leaves the row in `sending` for the stuck-row step.
- **Logging:** unchanged: kind, language, exception type and status code, never the recipient or a message.
- Update email.md's "doesn't throw" wording ([checklist](#cleanup-checklist)).

## Worker (Jobs host)

`SendEmailsJob` is a Hangfire recurring job with the 6-field cron `*/5 * * * * *`. Hangfire 1.8.25 reads six parts as `CronFormat.IncludeSeconds` (`RecurringJobEntity.ParseCronExpression`). Set `BackgroundJobServerOptions.SchedulePollingInterval` to 5 seconds, because the `RecurringJobScheduler` polls on it (default 15 s) and would otherwise miss ticks.

- **Retries belong to the row:** `[AutomaticRetry(Attempts = 0)]`, so Hangfire never stacks its own retries on the row's.
- **No overlap:** `[DisableConcurrentExecution(5)]`. The claim is what really guards it ([Hangfire's own note](https://docs.hangfire.io/en/latest/background-processing/throttling.html)); the attribute only saves work.
- **Job class:** thin, per [jobs.md](../backend/docs/jobs.md#job-classes): it sends `SendDueEmailsCommand` and returns.

### Each pass

1. **Recover stuck rows.** A row in `sending` with `last_attempt_at` older than 5 minutes (the 2-minute SMTP timeout plus a margin) goes back to `pending` with `last_error = 'SendingTimedOut'`, if its attempts are left. If its `last_error` already is `SendingTimedOut`, or attempts are used up, it becomes `failed`. At worst that is two emails, and the newer link supersedes the older.
2. **Claim.** Steps 2 to 6 run in one transaction, committed before any SMTP traffic. A compare-and-set `UPDATE`; the select may use `FOR UPDATE SKIP LOCKED` but the lock never outlives the commit:

   ```sql
   WITH due AS (
     SELECT id FROM app.email_requests
     WHERE status = 'pending' AND next_attempt_at <= @now
     ORDER BY next_attempt_at LIMIT @batch
     FOR UPDATE SKIP LOCKED)
   UPDATE app.email_requests r
   SET status = 'sending', attempt_count = r.attempt_count + 1, last_attempt_at = @now
   FROM due WHERE r.id = due.id AND r.status = 'pending'
   RETURNING r.id, r.kind, r.account_id, r.email, r.attempt_count;
   ```

   `@now` is `IClock`, so `FakeClock` drives the tests. `@batch` is 20 (a constant).

3. **Coalesce**, in the same transaction. For each kind and account (or address), only the newest request survives, by `created_at` then `id`. Older `pending` and just-claimed rows become `superseded` and are never sent.
4. **Resolve** each claimed row to an account and its preferred language:
   - an unknown address (resend, forgot-password): delete the row, send nothing;
   - resend to an already-confirmed account: delete the row, send nothing;
   - reset to an unconfirmed account: security.md doesn't say yet. Decide with the user at implementation and write the rule in [security.md](security.md#accounts) first.
5. **Create the token** through ASP.NET Core Identity's `EmailLinkTokenProvider`, in the same transaction. Only the SHA-256 hash is stored and the new link replaces the old one. `AccountAlreadyExists` has no token.
6. **Build the link:** `<Links:FrontendBaseUrl>/confirm-email?id=<AccountIdentityId>&token=<base64url>`, or `/reset-password?id=…&token=…`. The plaintext token lives only in memory.
7. **Send** through `IEmailSender`, in the account's language, after that transaction has committed.
8. **Record** in a second short transaction: `sent` with `sent_at`, or the retry decision below.

### Retry policy

Configured as `Email:Retry:<Kind>` with `Attempts` and `Delays` (a list of `TimeSpan`, one per attempt, the delay before that attempt), in the Jobs host's `appsettings.json`, validated at start (`ValidateOnStart`; `Delays` has `Attempts` entries, all not negative, the first 0).

| Kind                   | Attempts | Delays (minutes)     | Why                     |
| ---------------------- | -------- | -------------------- | ----------------------- |
| `PasswordReset`        | 4        | 0, 1, 5, 15          | its link lasts 1 hour   |
| `EmailConfirmation`    | 6        | 0, 1, 5, 15, 60, 240 | its link lasts 24 hours |
| `AccountAlreadyExists` | 3        | 0, 5, 30             | no link                 |

`Retryable` with attempts left: status `pending`, `next_attempt_at` = now plus the next delay, `last_error` set. `Permanent`, or the last attempt used: `failed`, logged at Error with the kind and language only.

### Purge

`PurgeEmailRequestsJob` runs daily (cron `0 3 * * *`, UTC) and deletes `sent`, `superseded` and `failed` rows older than 30 days by `created_at`.

## Tests

The Api tests stop at the row. Emails are never read in them.

- **Api.IntegrationTests (`Accounts/`):**
  - register writes exactly one `pending` row of the right kind, for the new or the existing account;
  - the response for a taken email is identical and no second account exists;
  - resend writes a row keyed by the address, for any address;
  - confirm-email, with links issued directly through test support (`EmailLinkTokenProvider`): success, second use, altered link, another account's link, expiry;
  - a password breaking the rules returns 400 ProblemDetails with field errors.
- **Worker tests** (Application.Tests for the policy; Infrastructure.IntegrationTests `Email/` for the outbox, with seeded rows, `FakeClock` and a capturing fake `IEmailSender`):
  - claiming, including two passes that never claim one row twice;
  - coalescing;
  - unknown and already-confirmed addresses dropped;
  - only the token hash stored, with the link shape exact;
  - the language from the account;
  - each kind's retry policy and its last attempt;
  - 4xx retried, 5xx `failed`;
  - stuck rows, once and twice;
  - the purge;
  - no plaintext token in any table.
- **Jobs.IntegrationTests:** one test that both recurring jobs are registered with the right cron.
- **SmtpEmailSender tests:** the new `SendResult` outcomes against `ScriptedSmtpServer`, and the Message-Id local part.
- **Not here:** "the email comes in the right language" through the whole flow (the worker test covers the language) and the 5-per-hour email rate limit (E6).
